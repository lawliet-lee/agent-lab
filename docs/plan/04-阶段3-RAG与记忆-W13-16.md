# 阶段 3 · 检索增强与记忆（W13–W16）

目标：把"能查资料、能记住上下文"的能力加进 Agent，并且能用数据说明检索质量提升了多少。

这是招聘 JD 里出现频率最高的一块，也是面试被追问最狠的一块。不要只做到"跑通"，要做到"能对比"。

---

## W13 · RAG 的地基：数据、切分、向量

本周产出：索引构建脚本 + 一个能返回 top-k 的检索原型。

| 日 | 时长 | 今天做什么 | ☐ |
|---|---|---|---|
| 周一 | 60' | 建立正确的心智模型：RAG 是"把知识从模型参数搬到外部库，推理时实时检索注入"。同时写清它什么时候**不该**用——简单任务、纯推理任务、或上下文本来塞得下的场景，以及它与长上下文、微调的取舍。 | ☐ |
| 周二 | 60' | 文档解析与清洗：PDF / HTML / Markdown 各拿 3 份真实文档，处理页眉页脚、表格、乱码。脏数据是 RAG 失败第一原因。 | ☐ |
| 周三 | 60' | 切分策略实验：固定长度 / 递归分隔符 / 按结构（标题、代码块）切。chunk size 与 overlap 各设 3 档，为每档留一份可视化样例。 | ☐ |
| 周四 | 60' | Embedding：调一个 embedding 接口，理解维度、相似度度量、归一化。写一个"同义句应该近、主题无关应该远"的验证小实验。 | ☐ |
| 周五 | 60' | 向量存储落地：pgvector（你熟 SQL，推荐）或 Qdrant 二选一，本地跑起来，把 chunk + 向量 + 元数据入库。 | ☐ |
| 周六 | 120' | 写 `build_index.py`（解析→切分→向量化→入库，支持增量重跑）+ `search.py` 原型，命令行输入问题返回 top-k 片段与分数。 | ☐ |
| 周日 | — | 休息。 | ☐ |

## W14 · 检索质量（本周是全阶段核心）

本周产出：三种检索方案的效果对比表，这是你简历上最有说服力的一个数字。

| 日 | 时长 | 今天做什么 | ☐ |
|---|---|---|---|
| 周一 | 60' | 先建评估再谈优化：标 20 条真实问答对（问题 → 应命中的文档/段落），算 recall@k 与 MRR。**没标注就没有对比。** | ☐ |
| 周二 | 60' | 关键词检索（BM25）与向量检索，实现混合并用 RRF 融合。实测哪些查询只有 BM25 能命中（专有名词、编号、代码符号）。 | ☐ |
| 周三 | 60' | Rerank：粗召回 top-50 → 精排 top-5。测 rerank 带来的质量增益与额外延迟/成本。 | ☐ |
| 周四 | 60' | 查询改写：multi-query、HyDE、子问题分解各实现一种，用于"用户问法和文档措辞不一致"的场景。 | ☐ |
| 周五 | 60' | 元数据过滤与权限边界：按部门/时间/密级过滤。**权限过滤必须在检索层，不能靠提示词说"不要透露"。** | ☐ |
| 周六 | 120' | 跑完整对比：纯向量 vs 混合 vs 混合+rerank（±查询改写），同评测集出表格，含 recall@5、MRR、平均延迟、单次成本。 | ☐ |
| 周日 | — | 休息。 | ☐ |

这张表值得放进 W23 的技术文里。多数候选人只会说"我做过 RAG"，而你能说"混合检索加 rerank 让 recall@5 从 0.62 提到 0.81，代价是延迟 +180ms"。

### 阶段 3 验收

- ☐ 有一份 ≥20 条标注的检索评测集，以及三方案对比表（含延迟与成本）。
- ☐ 答案带来源引用，且低置信时能拒答（有负样本验证）。
- ☐ 说清"检索层权限过滤"与"提示词层禁止透露"的差别为什么是安全事故级别。
- ☐ 项目一 v2 已接入检索与记忆，README 更新。
- ☐ 项目二 PRD 已写完。
