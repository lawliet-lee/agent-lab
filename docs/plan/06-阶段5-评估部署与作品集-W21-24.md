# 阶段 5 · 评估、部署与出手（W21–W24）

目标：把两个项目从"能跑"变成"能被质疑也站得住"，并在第 24 周末把成果交付出去（内部转岗沟通或外部投递）。

判断依据类内容——评估、可观测、成本——是 AI 应用岗与"调 API 的人"的分水岭，优先级高于任何新技术。

---

## W21 · 评估与可观测性

本周产出：一份 30–50 条的评测集 + 两个项目都接入 trace + 一份评测报告。

| 日 | 时长 | 今天做什么 | ☐ |
|---|---|---|---|
| 周一 | 60' | 建立指标体系：最终答案正确率、工具调用正确率（该不该调、参数对不对）、步数效率、成本、延迟。理解为什么"只看最终输出对不对"无法定位 Agent 的问题。 | ☐ |
| 周二 | 60' | 接一个追踪平台（自建友好选 Langfuse）：trace / span / metadata，把 W09 手写的 JSONL 升级成可视化链路，看清一次多步执行的全貌。 | ☐ |
| 周三 | 60' | 建评测集：30–50 条真实问答，**必须包含失败样例与刁钻样例**，标注期望行为（含"应拒答""应调用某工具"）。 | ☐ |
| 周四 | 60' | LLM-as-judge：写评分 rubric（准确性、引用忠实度、是否越权），人工抽检 10 条校准评判模型偏差。知道 judge 也会错，所以关键结论要人工复核。 | ☐ |
| 周五 | 60' | 回归门：一条命令跑完整评测集，输出与上一版的分数对比。改任何提示词或工具描述前后都跑一次。 | ☐ |
| 周六 | 120' | 两个项目全量接入追踪，出评测报告：当前通过率、top 3 失败模式、修一个之后的提升数字。 | ☐ |
| 周日 | — | 休息。 | ☐ |

## W22 · 部署、成本与安全

本周产出：项目一部署到公网，拿到可访问 URL。

| 日 | 时长 | 今天做什么 | ☐ |
|---|---|---|---|
| 周一 | 60' | FastAPI 服务化：请求/响应模型、流式 SSE 返回、后台任务、超时与取消。 | ☐ |
| 周二 | 60' | 容器化与配置分离：Dockerfile、多环境配置、密钥注入（别写进镜像）。 | ☐ |
| 周三 | 60' | 成本与延迟治理：模型分级路由（简单任务走便宜模型）、prompt caching 命中率、并发与队列上限、单次请求成本看板。拿真实数据说明"我优化掉了多少"。 | ☐ |

### 阶段 5 验收（也就是全计划验收）

- ☐ 项目一有公网 URL，能被陌生人访问使用。
- ☐ 有 30 条以上评测集，一条命令能出回归分数对比。
- ☐ 有 trace 可视化，能演示"一次失败是怎么被定位的"。
- ☐ 有一篇公开技术文与一个成形的作品集页。
- ☐ 简历与投递/转岗材料已发出，不是"等我再学两周"。

### 总复盘四问（必须写答案，不能只在脑子里过）

1. **时间账**：计划 168 小时，`git log` 显示实际投入多少？缺口集中在哪个阶段、什么原因？
2. **有效方法**：哪三件事对能力提升贡献最大？（通常有手写循环、评测集、对比实验）
3. **该砍的**：哪些内容是学了但完全没用上的？下一轮直接从课表里删掉。
4. **最强叙事**：用一句话说明"我和只会调 API 的人差别在哪"。这句话就是你面试和转岗的主线。

## 24 周之后

三条现实路径，按成功概率排序：

**内部转岗（最推荐）** —— 你已经有跑在公网的项目和业务侧真实反馈，带着"我想在现有系统里做这件事"去谈，比外部投递阻力小得多，且不浪费你已有的业务熟悉度。

**外部 AI 应用 / Agent 工程岗** —— 定位是"有扎实后端功底的 AI 应用工程师"，而不是算法岗。面试主战场就是 W21 的评估与 W19 的可靠性，把这两块讲透。

**留在现职但换技术栈** —— 把两个项目对接到真实业务流程，成为团队里那个"能落地 AI 能力的人"。这条路最省力，收益也最慢，但往往是最先发生的一条。

无论哪条，请继续保留每周的学习块——Agent 基础设施一年内还会变好几轮，W20 那张框架选型表在 2027 年需要重写一遍。
