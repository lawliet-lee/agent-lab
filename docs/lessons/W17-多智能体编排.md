## 周一 · 先建立怀疑

**本质**：多智能体不是能力升级，是架构妥协。单 Agent 你只维护一份上下文、一个终止条件、一条 trace；拆成 N 个，这三样全变 N 份且互相污染。同等模型能力下"更多 Agent"通常降低而非提高端到端成功率——除非你撞到了单 Agent 撞不到的墙。

**Java 视角**：这是"要不要拆微服务"换了个皮。单体里一个方法调用能解决的事拆成三个服务，代价是分布式事务、链路追踪、契约版本；Agent 里的对应物是状态传递、trace 归属、交接协议。判断标准一样：拆分由约束驱动，不由"架构好看"驱动。

**核心讲解**

拆分只有三个正当理由，每个都要能说出"单 Agent 具体死在哪一步"：

1. **上下文隔离（context isolation）**：子任务灌入大量低价值 token（整份日志、全量检索片段）会挤掉主任务注意力，把它隔离进子 Agent、主 Agent 只收摘要。这是唯一"用 token 换准确率"的正经理由。判据：中间上下文 > 最终所需信息量约 10 倍。
2. **并行（parallelism）**：多个相互独立、各自动辄 20 秒以上的子任务，串行延迟线性累加。判据：无数据依赖，且耗时由外部 I/O 主导而非模型推理主导。
3. **不同权限域（permission domain）**：最硬的一条，而且是安全理由不是性能理由。"能读生产库"和"能改工单状态"不该共存于一个上下文——模型幻觉调用时越权的就是它。硬性规则：**权限边界由工具挂载 + 执行前代码校验实现，绝不由"提示词里叫它别越权"实现**。

不该拆的信号，最典型的是"为了看起来高级"：Agent 的名字比任务规则还多却没有一条真实约束；所谓多智能体其实是固定输入输出的串行 LLM 调用（那是 workflow 步骤，写成函数即可）；你答不出"合并这两个 worker 会坏在哪一步"；主 Agent 的全部工作是"转述用户原话、再转述子 Agent 原话"——那是空转，只多两次信息丢失。层级（hierarchical，supervisor 上再套 supervisor）每加一层多一次摘要，约束丢失概率按层数复合；项目二锁死两层。

**代码**
```python
"""拆分决策强制留痕：写不出可复现的 justification 就不许拆。"""
from __future__ import annotations

from enum import Enum
from pydantic import BaseModel, Field, ValidationInfo, field_validator

class SplitReason(str, Enum):
    CONTEXT_ISOLATION = "context_isolation"
    PARALLELISM = "parallelism"
    PERMISSION_DOMAIN = "permission_domain"

class SplitDecision(BaseModel):
    task: str
    reasons: list[SplitReason] = Field(default_factory=list)
    justification: dict[SplitReason, str] = Field(default_factory=dict)  # 理由 → 单 Agent 失败的具体步骤

    @field_validator("justification")
    @classmethod
    def needs_evidence(cls, v: dict[SplitReason, str], info: ValidationInfo) -> dict[SplitReason, str]:
        for r in info.data.get("reasons", []):
            if len(v.get(r, "")) < 20:  # 空话拦不住机器，但把"只是想拆"的成本抬到必须写失败步骤
                raise ValueError(f"理由 {r.value} 缺少可复现的单 Agent 失败描述")
        return v
```

## 周二 · supervisor：分派、汇总、终止

**本质**：supervisor 是只做两件事的循环——把目标翻译成**可执行的任务描述**派给 worker，把 worker 返回**压缩成决策所需的少量事实**再决定下一步。它不碰业务工具，所以全部风险都在这两次翻译上：派错了和收错了。

**Java 视角**：它就是 saga coordinator——不访库、不调下游，只发起、等待、判定。你写 saga 时绝不会让协调器靠"猜"决定流转，这里同理：判定必须是确定的代码。

**核心讲解**

**分派协议**（dispatch protocol）必须是固定字段的结构而不是自由文本：`goal`（这步要什么）、`inputs`（可复用事实与引用 ID，不是整段历史）、`expected_output`（返回结构名）、`constraints`（边界与禁止项）、`budget`（最多几步、最多花多少）。自由文本传话时 worker 会自行补全"隐含目标"，补出来常是幻觉；散落在正文里的约束会被摘要吃掉（周四整日打这个）。

**汇总时的三种信息丢失**，全部可复现：**约束丢失**（worker 报"查得 12 条异常"同时丢掉"仅统计 2026Q2 分区"，下一轮据此派发跨分区任务）；**不确定性丢失**（worker 检索失败用了兜底答案，摘要只留结论——修法是强制 `confidence` + `evidence`，无证据的结论不许进下一轮）；**数字丢失**（"发现若干问题"——修法是汇总走结构化输出，别让模型写散文再由 supervisor 读回去）。

**终止条件**：硬性规则是判定写在代码里，模型只能"建议"终止。四类同时装——① 完成＝结构化 `done` 且必要产物齐全（缺产物即未完成）；② 预算＝轮数/token/墙钟/成本四个都设，任一越界即停；③ 无进展＝连续 K 轮"事实集合指纹"不变或无新工具调用（死循环的唯一解药）；④ 失败上限＝连续 N 次 worker 失败即停。

**代码**
```python
from __future__ import annotations

import hashlib, json
from typing import Literal
from pydantic import BaseModel, Field

class TaskAssignment(BaseModel):
    assignee: str
    goal: str
    inputs: list[str] = Field(default_factory=list)     # 只放引用 ID，不放整段历史
    expected_output: str                                 # worker 返回结构名，让"收错"在类型层暴露
    constraints: list[str] = Field(default_factory=list)
    budget: dict[str, int] = Field(default_factory=dict)

class WorkerResult(BaseModel):
    ok: bool
    facts: list[str] = Field(default_factory=list)
    constraints_honored: list[str] = Field(default_factory=list)  # 原样回传，不许在 worker 侧摘要掉
    confidence: Literal["high", "medium", "low"] = "low"
    evidence: list[str] = Field(default_factory=list)             # 无证据的结论不许进入下一轮

def state_fingerprint(history: list[tuple[TaskAssignment, WorkerResult]]) -> str:
    """对事实集合排序后 hash：轮次文字变化不影响它，因此能识别'原地打转'。"""
    facts = sorted({f for _, r in history for f in r.facts})
    return hashlib.sha256(json.dumps(facts, ensure_ascii=False).encode()).hexdigest()[:16]

def should_stop(history: list[tuple[TaskAssignment, WorkerResult]], *, tokens: int, elapsed_s: float) -> str | None:
    """返回终止原因，None 表示继续。阈值按项目二实测调，但四类一个不许省。"""
    if tokens > 60_000 or elapsed_s > 300 or len(history) >= 8:
        return "budget"
    if sum(1 for _, r in history if not r.ok) >= 3:
        return "max_failures"
    if len(history) >= 3 and len({state_fingerprint(history[: i + 1]) for i in range(len(history) - 3, len(history))}) == 1:
        return "no_progress"
    return None
```
`decide_next` 自己写：把 history 压成 `[{goal, constraints, facts}]` 交给模型，要求只输出符合 `TaskAssignment` 的 JSON 或 `null`；解析失败计一次 `invalid_dispatch`。主循环顺序固定：`should_stop` → `decide_next` → 校验 `assignee` 存在（不存在即停，不重试）→ 执行 worker → 追加 history。

## 周三 · 并行 worker：并发上限、双层超时、失败聚合

**本质**：并行不是加速按钮，是把顺序代码的"错了就停"变成并发代码的"谁错了、要不要等其他、其他能等多久"。今天的产出物是一段你敢在生产里跑的 fan-out / fan-in 代码。

**Java 视角**：`asyncio.Semaphore` ≈ 线程池最大容量 + RateLimiter；总超时对应"全局超时 vs 单接口超时"必须分别设；失败聚合对应 `CompletableFuture.allOf` 与 `anyOf` 的取舍。

**核心讲解**

- **并发上限必须显式**。不设上限的 fan-out 一次打满下游：LLM 供应商 RPM/TPM 限流、内部 API 连接池、数据库连接数。经验值：LLM 类 worker 2–4（被限流后的重试风暴比串行更慢），纯 I/O 类 5–10。
- **两层超时语义不同**。单任务超时管"一个 worker 卡死"，总超时管"整个请求无限挂着"。只设单任务超时会出事：8 个任务各 40 秒、并发压到 2 → 实际 160 秒。外层超时触发后**必须真的取消所有子任务**，否则 Agent 在后台继续调工具、继续写数据。
- **结构化并发**。用 `asyncio.TaskGroup`（3.11+）而非裸 `gather`：异常或外层超时时它取消同组任务并等它们退出，杜绝"主流程已返回、后台还在写库"。
- **失败聚合策略要写进代码**：`all_required`（任一失败即整体失败）、`best_effort`（收多少算多少但显式标注缺了谁）、`quorum`（至少 M 个成功）。项目二默认 `best_effort`——分诊场景少一个服务的结论仍有价值，但把 `degraded` 当 `ok` 会让 supervisor 过度自信。
- **worker 里不许有同步阻塞调用，且每个 run 要有 `run_id`**。一个 `requests.get` 冻住整个事件循环，表现是"并发 4 但总耗时等于串行"，诊断：`loop.slow_callback_duration = 0.1` 看告警。并发下日志混在一起，没有 `run_id` 前缀，W21 接追踪时 span 归不了位。

**代码**
```python
from __future__ import annotations

import asyncio, uuid
from enum import Enum
from typing import Awaitable, Callable
from pydantic import BaseModel
from src.agent.supervisor import TaskAssignment, WorkerResult

class AggregateMode(str, Enum):
    ALL_REQUIRED = "all_required"
    BEST_EFFORT = "best_effort"   # 项目二默认：允许缺项，但必须显式暴露缺了谁
    QUORUM = "quorum"

class WorkerRun(BaseModel):
    task: TaskAssignment
    result: WorkerResult | None = None
    error: str | None = None   # 失败必须是数据，不能是异常
    run_id: str = ""           # trace 归属：并发下日志无前缀就无法归位

Worker = Callable[[TaskAssignment], Awaitable[WorkerResult]]

async def _run_one(w: Worker, sem: asyncio.Semaphore, task: TaskAssignment, timeout_s: float) -> WorkerRun:
    run = WorkerRun(task=task, run_id=f"{task.assignee}-{uuid.uuid4().hex[:8]}")
    async with sem:  # 令牌在这里拿：排队时间不计入任务超时，否则并发数会伪装成超时
        try:
            async with asyncio.timeout(timeout_s):
                run.result = await w(task)
        except TimeoutError:
            run.error = f"timeout_after_{timeout_s}s"
        except asyncio.CancelledError:
            raise  # 被总超时取消：交还信号，由下面的收集器补记
        except Exception as exc:  # noqa: BLE001 —— 吃成数据，不污染兄弟任务
            run.error = f"{type(exc).__name__}: {exc}"[:300]
    return run

async def run_workers(
    workers: dict[str, Worker], tasks: list[TaskAssignment], *,
    max_concurrency: int = 3, per_task_timeout: float = 45.0, total_timeout: float = 120.0,
    mode: AggregateMode = AggregateMode.BEST_EFFORT, quorum: int = 0,
) -> tuple[list[WorkerRun], str]:
    """per_task_timeout 必须显著小于 total_timeout。判定 degraded 时上层必须带缺项继续，禁止当成功。"""
    sem, futures = asyncio.Semaphore(max_concurrency), []
    timed_out, fatal = False, None
    try:
        async with asyncio.timeout(total_timeout):
            async with asyncio.TaskGroup() as tg:  # 结构化并发：超时即取消并等待全部退出
                for t in tasks:
                    if (w := workers.get(t.assignee)) is not None:
                        futures.append((t, tg.create_task(_run_one(w, sem, t, per_task_timeout))))
    except* TimeoutError:
        timed_out = True   # 走到这里子任务已全部取消，不会再有后台写入
    except* Exception as eg:
        fatal = str(eg)[:300]  # TaskGroup 兜不住的实现级错误：留痕判失败，不许静默

    runs: list[WorkerRun] = []  # TaskGroup 不交还结果：三种终态都要记账，缺谁必须显式可见
    for t, fut in futures:
        if fut.cancelled():
            runs.append(WorkerRun(task=t, error="cancelled_by_total_timeout"))
        elif exc := fut.exception():  # 退出 TaskGroup 后所有 future 必已 settle
            runs.append(WorkerRun(task=t, error=f"{type(exc).__name__}: {exc}"[:300]))
        else:
            runs.append(fut.result())
    ok = sum(1 for r in runs if r.result and r.result.ok)
    if fatal is not None or (mode is AggregateMode.ALL_REQUIRED and (timed_out or ok < len(tasks))):
        return runs, "failed"
    if mode is AggregateMode.QUORUM and ok < quorum:
        return runs, "failed"
    return (runs, "degraded") if (timed_out or ok < len(tasks)) else (runs, "ok")
```

## 周四 · 状态传递：共享 state vs 消息传递

**本质**：两种方式各有一种失败——共享 state 的失败是**并发写互相覆盖且无报错**，消息传递的失败是**边界处信息丢失**。今天你要亲手制造后者再修掉它。

**Java 视角**：共享可变 state 就是多线程共写一个 `HashMap`，Java 里怎么防（不可变消息 + 显式合并）这里就怎么防；消息传递像跨服务传 DTO，必填字段要校验，这里同理。

**核心讲解**

**共享 state**（LangGraph 里那个 state dict + reducer 就是它）：优点是零序列化成本、worker 能看到彼此成果；风险是两个 worker 同轮写同一键，后写覆盖先写且全程无报错。规则：每个键必须显式指定 reducer（`add_messages` 这类追加语义或自定义 merge）；**没有 reducer 的键视为只读**；写冲突要被检测出来而不是静默 last-write-wins。

**消息传递**（message passing）：每个 worker 只拿自己需要的字段，天然并发安全，但每次交接都是有损压缩。项目二的具体失效链，今天就复现：原始约束是"只允许查询 2026Q2 分区；任何写操作先回主 Agent 确认"。diagnoser 的结论被摘要成一句"定位到 order-service 的 12 笔超时"——约束整段消失；supervisor 据此派发"补充查询近 90 天同类超时"，worker 跨分区扫了生产库；摘要里同样没带"已执行过的写操作范围"，第二个 worker 又重发了一次相同告警通知。

三个环节是同一个错误：**约束与权限走了自然语言通道，而自然语言通道允许被摘要**。修法不是"提示词里加一句务必保留"（照样丢），而是三条硬性规则：① 约束与权限不进摘要字段，进 typed field，组装上下文时由代码原样拼接，模型无权改写；② 工具执行**之前**加确定性校验门，用结构化规则检查入参（时间范围、资源前缀、是否写操作），违规即拒绝并回一条模型可读的错误——边界校验只能在代码里；③ 交接信息量设下限，`facts` 为空但文本很长的消息判为无效并计数。

**代码**
```python
from __future__ import annotations

from datetime import date
from typing import Any, Literal
from pydantic import BaseModel, Field

class Constraints(BaseModel):
    time_range: tuple[date, date] | None = None           # 结构化边界，摘要吃不掉它
    allowed_source_prefixes: list[str] = Field(default_factory=lambda: ["ticket/"])
    allow_write: bool = False

class AgentMessage(BaseModel):
    sender: str
    facts: list[str] = Field(default_factory=list)         # 唯一参与下一轮决策的字段
    summary: str = ""                                       # 只给人读
    constraints: Constraints
    permission: Literal["read_only", "read_write"] = "read_only"
    already_executed_effects: list[str] = Field(default_factory=list)  # 副作用清单，防重复执行

def enforce(msg: AgentMessage, tool: str, args: dict[str, Any]) -> str | None:
    """工具执行前的确定性校验门。返回 None 放行，返回文本即拒绝（该文本回给模型）。"""
    c = msg.constraints
    if tool.startswith("write_") and not (c.allow_write and msg.permission == "read_write"):
        return f"工具 {tool} 是写操作，本次权限 {msg.permission}，请回主 Agent 申请确认。"
    if "since" in args and c.time_range is not None:
        since = date.fromisoformat(str(args["since"]))
        if not c.time_range[0] <= since <= c.time_range[1]:
            return f"入参 since={since} 越界，允许范围 {c.time_range}（不可协商）。"
    if "source" in args and not any(str(args["source"]).startswith(p) for p in c.allowed_source_prefixes):
        return f"数据源 {args['source']} 不在白名单 {c.allowed_source_prefixes} 内。"
    return None
```
reducer 自己写 `merge_results(existing, new)`：`facts` 为空且 `summary` 超长即丢弃并计数；否则追加而非覆盖；约束冲突时取更严的一侧，绝不静默放宽。再加一条硬规则——`summary` 里出现数字而 `facts` 为空的消息直接判无效，数字只能活在结构化字段里，否则下一轮必然从散文里抽出漂移的数字。

## 周五 · handoff 语义

**本质**：handoff（转交）是一次有损的进程交接。不是"把聊天记录发给下一个 Agent"，而是"把下游完成任务所必须的最小充分集交给它"。交接漏项是排障时最难归因的 bug——因为下游看起来一切正常。

**Java 视角**：跟跨服务传请求上下文同一个问题：传业务参数的同时必须传 traceId、租户身份、幂等键。最常见的生产事故是"下游丢了租户上下文，退化成默认租户"。Agent 里丢的是权限上下文，性质完全相同。

**核心讲解**

交接信封必须带四件东西，缺一即不许发出：

1. **目标（goal）**：交付什么 + 验收标准。"继续处理这个工单"无效，必须写成"给出根因候选 top3 与证据，不执行任何处置"。
2. **已做事实（established facts）**：已完成且有证据的结论，附引用 ID。是"事实"不是"过程"——别传尝试过但失败的 20 轮，那会诱导下游重复踩坑。
3. **未决约束与问题（open questions）**：尚未确认的假设、边界（时间范围、数据源、不得写入）、要下游回答的问题。这项最易丢，因为它描述"没有发生的事"，摘要时存在感最低。
4. **权限上下文（permission context）**：能用哪些工具、是否可写、代表哪个用户/角色、已执行过的副作用清单。硬性规则：**由代码从会话状态注入，不由模型生成**——模型无权在交接时扩大权限。

三类典型失败：传全量历史（成本爆炸 + 上游幻觉被下游当事实接受）；交接即重置（下游不知道发生过什么，重复执行副作用）；丢失调用者身份（审计断链，出事后查不到谁授权）。

**代码**
```python
from __future__ import annotations

from typing import Literal
from pydantic import BaseModel, Field, field_validator
from src.agent.state import Constraints

class HandoffEnvelope(BaseModel):
    goal: str
    acceptance: str                                          # 下游怎么判断自己完成了
    established_facts: list[str] = Field(default_factory=list)
    open_questions: list[str] = Field(default_factory=list)   # 描述"没发生的事"，最易丢，设必填
    constraints: Constraints
    allowed_tools: list[str] = Field(default_factory=list)    # ↓ 这四组由代码注入，模型不能填
    permission: Literal["read_only", "read_write"] = "read_only"
    acting_as: str = ""                                        # 审计身份，为空即拒绝交接
    already_executed_effects: list[str] = Field(default_factory=list)

    @field_validator("goal", "acceptance")
    @classmethod
    def must_be_specific(cls, v: str) -> str:
        if len(v.strip()) < 12:
            raise ValueError("目标/验收过于笼统，下游必然自行补全")
        return v

    @field_validator("allowed_tools", "acting_as")
    @classmethod
    def permission_required(cls, v: object) -> object:
        if not v:
            raise ValueError("缺少权限上下文，拒绝交接：下游会退化成默认权限运行")
        return v
```
构造函数 `build_handoff(...)` 的入参里必须有一个 `caller_ctx: dict`，它取自会话状态而非模型输出——这是权限注入的唯一可信来源。`render_for_llm(env)` 把信封渲染成下游提示词，末尾显式写"已执行副作用（不得重复）：……"，这是 W19 幂等机制的前身。

## 本周术语卡

| 术语 | 一句话解释 | 为什么重要 |
|---|---|---|
| orchestrator-worker / supervisor 模式 | 协调 Agent 只派活与判定，worker 执行 | supervisor 自己调工具即结构腐化信号 |
| context isolation（上下文隔离） | 高噪声中间过程关进子 Agent | 拆分三理由之一 |
| permission domain（权限域） | 不同 Agent 挂不同工具集与读写权限 | 唯一由安全驱动的理由，必须代码实现 |
| fan-out / fan-in | 并发派发再聚合 | 聚合策略决定失败怎么算 |
| concurrency limit（并发上限） | Semaphore 限制同时在跑的任务数 | LLM 类经验值 2–4，不是越大越好 |
| total vs per-task timeout | 总超时保护调用方，单任务超时保护卡死者 | 只设单任务超时会雪崩成"12 任务并发 3 = 160 秒" |
| structured concurrency（结构化并发） | TaskGroup 退出时保证子任务被取消并等待 | 防止接口已返回但后台继续写数据 |
| shared state vs message passing | 共写一份 state，或传不可变消息 | 前者失败是静默覆盖，后者失败是边界丢信息 |
| reducer | 指定同一 state 键如何合并 | 没写 reducer 的键应视为只读 |
| information loss on summarization | 摘要丢掉约束、置信度与数字 | 本周最难归因的失效链，修法是结构化 + 代码门 |
| handoff（转交） | 带结构化信封的任务交接 | 丢权限上下文＝下游以默认权限运行，等同跨租户事故 |
