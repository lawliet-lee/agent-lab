## 周一 · 先建立怀疑

**本质**

多智能体不是能力升级，是架构妥协。单个强模型配好工具，你只需要维护一份上下文、一个终止条件、一条 trace；拆成 N 个 Agent，这三样全变成 N 份，而且它们会互相污染。业界跑下来的经验是一致的：在同等模型能力下，"更多 Agent"通常降低而不是提高端到端成功率，除非你确实撞到了单 Agent 撞不到的那三堵墙。

**Java 视角**

这就是"要不要拆微服务"换了个皮。单体内一个方法调用能解决的事，你非要拆成三个服务，代价是分布式事务、链路追踪、契约版本管理——Agent 里对应物是幂等与状态传递、trace 归属、交接协议。判断标准也一样：拆分必须由约束驱动，不能由"架构好看"驱动。

**核心讲解**

拆分只有三个正当理由，每个都要能说出"单 Agent 具体死在哪"：

1. **上下文隔离（context isolation）**。单 Agent 的上下文里同时装着 5 个工具的 schema、3 段检索原文、20 轮历史。当某段子任务会灌入大量低价值 token（整份日志、全量文档片段），它会把模型的注意力挤掉。把这段隔离到子 Agent，主 Agent 只收摘要——这是唯一"用 token 换准确率"的正经理由。判据：子任务的中间上下文 > 主任务最终需要的信息量 10 倍。
2. **并行（parallelism）**。多个互相独立、各自耗时 20 秒以上的子任务（比对 3 个服务的错误日志、分别审 4 份配置），串行跑总延迟线性累加。判据：子任务之间无数据依赖，且单任务延迟由外部 I/O 主导而非模型推理主导。
3. **不同权限域（permission domain）**。这是最硬的一条，而且是安全理由不是性能理由。"能读生产数据库"和"能改工单状态"不该在同一个 Agent 的上下文里共存——因为模型一旦产生幻觉调用，越权的就是它。拆成两个 Agent，每个只挂载自己那一份工具，权限边界落在代码层而不是提示词层。硬性规则：**权限隔离必须由工具挂载与执行前校验实现，绝不能由"提示词里告诉它不要越权"实现**。

不该拆的信号，最典型的一个就是"为了让架构看起来高级"。具体表现为：

- 你给 Agent 起的名字比给任务写的规则多（`researcher` / `writer` / `critic` / `planner`，但没有一条真实的上下文或权限约束）。
- 所谓"多智能体"其实是把一次模型调用拆成三次串行调用，每次只是提示词不同——那是 workflow 的链式步骤，用图或函数编排就够，不需要 Agent 语义。
- 你无法回答"把这两个 worker 的提示词合并进一个 Agent，会坏在哪一步"。答不出来，就说明不需要拆。
- 拆完之后主 Agent 的全部工作变成"把用户原话转述给子 Agent，再把子 Agent 的原话转述回来"——那是空转，只增加了两次信息丢失。

层级（hierarchy，supervisor 之上再套 supervisor）：深度超过 2 层，每一层都要做一次摘要，约束丢失概率按层数复合。项目二就锁定 supervisor → worker 两层，不许加第三层。

```python
"""拆分决策的强制记录：写不出 justification 就不许拆。"""
from __future__ import annotations

from enum import Enum
from typing import Literal

from pydantic import BaseModel, Field, ValidationInfo, field_validator


class SplitReason(str, Enum):
    CONTEXT_ISOLATION = "context_isolation"
    PARALLELISM = "parallelism"
    PERMISSION_DOMAIN = "permission_domain"


class AgentSpec(BaseModel):
    name: str
    # 只挂自己那一份工具；工具集合为空 = 这个 Agent 只是提示词的花瓶
    tools: list[str] = Field(default_factory=list)
    # 权限域：读写标记 + 允许的数据源前缀，执行层会用它做硬校验
    write_allowed: bool = False
    allowed_sources: list[str] = Field(default_factory=list)


class SplitDecision(BaseModel):
    task: str
    reasons: list[SplitReason] = Field(default_factory=list)
    # 每条理由必须写明：单 Agent 具体死在哪一步（可复现的证据，不是推测）
    justification: dict[SplitReason, str] = Field(default_factory=dict)
    agents: list[AgentSpec] = Field(default_factory=list)
    reject_signals_checked: list[str] = Field(default_factory=list)

    @field_validator("agents")
    @classmethod
    def at_least_two_agents(cls, v: list[AgentSpec]) -> list[AgentSpec]:
        if len(v) < 2:
            raise ValueError("拆了却只有 1 个 Agent，直接退回单 Agent 实现")
        return v

    @field_validator("justification")
    @classmethod
    def every_reason_must_be_evidenced(cls, v: dict[SplitReason, str], info: ValidationInfo) -> dict[SplitReason, str]:
        reasons = info.data.get("reasons", [])
        for r in reasons:
            # 空话拦不住机器，但能把"我只是想拆"这一步成本抬高到必须写具体
            if len(v.get(r, "")) < 20:
                raise ValueError(f"理由 {r.value} 缺少可复现的单 Agent 失败描述")
        return v


DECISION = SplitDecision(
    task="值班告警分诊：定位异常服务并给出处置建议",
    reasons=[SplitReason.PERMISSION_DOMAIN],
    justification={
        SplitReason.PERMISSION_DOMAIN: (
            "单 Agent 同时挂载 prod-sql-read 与 ticket-write：实测在告警文本含 "
            "'把这条工单关掉' 时直接调用写工具，未经任何确认"
        )
    },
    agents=[
        AgentSpec(name="diagnoser", tools=["sql_read", "log_search"], allowed_sources=["prod/*"]),
        AgentSpec(name="actioner", tools=["ticket_write"], write_allowed=True, allowed_sources=["ticket/*"]),
    ],
    reject_signals_checked=["是否只是提示词不同的串行调用", "合并两个 worker 会坏在哪一步"],
)
```

## 周二 · supervisor / 层级模式的实现要点

**本质**

supervisor 是一个只做两件事的循环：把目标翻译成**可执行的任务描述**派给 worker；把 worker 的返回**压缩成决策所需的少量事实**再决定下一步。它自己不碰业务工具，所以它的全部风险都在两个"翻译动作"上——派错了和收错了。

**Java 视角**

supervisor 就是编排层的 saga coordinator：它不访问数据库、不调下游接口，只负责发起、等待、判定。你写 saga 时绝不会让 coordinator 靠"猜"来决定下一步流转，这里同理——判定条件必须是确定的代码。

**核心讲解**

**分派任务的描述协议。** supervisor 给 worker 的不能是一段自由文本，必须是一个结构体，字段固定五项：`goal`（这一步要得到什么）、`inputs`（可复用的事实与引用 ID，不是整段历史）、`expected_output`（返回的 schema 名）、`constraints`（不许做什么、边界在哪）、`budget`（最多几步、最多花多少 token）。原因很实际：自由文本传话时，worker 会自己补全"隐含目标"，补出来的往往是幻觉；而 `constraints` 一旦以自然语言散落在正文里，就会被 worker 的摘要环节吃掉（周四整日就在打这个）。

**汇总时的信息丢失。** 三种典型丢失，全部可复现：

- **约束丢失**：worker 报告"已查得 12 条异常"，但把"仅统计 2026Q2 分区"这条约束丢掉了，下一轮 supervisor 基于这个结论又派发了跨分区任务。
- **不确定性丢失**：worker 内部其实检索失败、用了兜底答案，但摘要里只留了结论。修法：`WorkerResult` 强制带 `confidence` 与 `evidence`，没有证据字段的结论不许进入下一轮。
- **计数/集合丢失**：worker 说"发现若干问题"。修法是让汇总走结构化输出，而不是让模型写散文再由 supervisor 读。

**终止条件。** 硬性规则：终止判定写在代码里，模型只能"建议"终止。四类条件必须同时装：

1. **完成**：结构化 `done` 标志 + 必要产物齐全（缺产物即视为未完成）。
2. **预算**：最大轮数、累计 token、墙钟时间、累计成本——四个都要设，任一越界即终止。
3. **无进展**：连续 K 轮状态指纹（对关键产物做 hash）不变，或没有新的工具调用发生。这是死循环的唯一解药。
4. **失败上限**：连续 worker 失败次数超阈值即终止，不要"再试一次也许就对了"。

**代码**

```python
from __future__ import annotations

import hashlib
import json
from typing import Literal, Protocol

from pydantic import BaseModel, Field


class TaskAssignment(BaseModel):
    """supervisor 派发的不是自然语言，是协议。"""

    assignee: str
    goal: str
    inputs: list[str] = Field(default_factory=list)  # 只放引用 ID，不放整段历史
    expected_output: str  # worker 返回结构的名称
    constraints: list[str] = Field(default_factory=list)
    budget: dict[str, int] = Field(default_factory=dict)


class WorkerResult(BaseModel):
    ok: bool
    facts: list[str] = Field(default_factory=list)
    # 约束与不确定性必须原样回传，不许在 worker 侧摘要掉
    constraints_honored: list[str] = Field(default_factory=list)
    confidence: Literal["high", "medium", "low"] = "low"
    evidence: list[str] = Field(default_factory=list)
    steps_used: int = 0


class ChatModel(Protocol):
    def complete(self, system: str, payload: str) -> str: ...  # 沿用 W10 的客户端封装


def decide_next(llm: ChatModel, objective: str, history: list[tuple[TaskAssignment, WorkerResult]]) -> TaskAssignment | None:
    """让模型只做'选下一步做什么'，产物用结构化输出约束回 TaskAssignment。"""
    digest = json.dumps(
        [{"goal": a.goal, "constraints": a.constraints, "facts": r.facts, "conf": r.confidence} for a, r in history],
        ensure_ascii=False,
    )
    raw = llm.complete(
        "你是 supervisor。只输出符合 TaskAssignment 的 JSON；目标达成时输出 null。不要转述用户原话。",
        f"目标：{objective}\n已有结果：{digest}",
    )
    if raw.strip().lower() in {"null", "none"}:
        return None
    return TaskAssignment.model_validate(json.loads(raw))


def state_fingerprint(history: list[tuple[TaskAssignment, WorkerResult]]) -> str:
    """无进展检测的锚：对事实集合取稳定 hash，轮次文字变化不影响它。"""
    all_facts = sorted({f for _, r in history for f in r.facts})
    return hashlib.sha256(json.dumps(all_facts, ensure_ascii=False).encode()).hexdigest()[:16]


def should_stop(history: list[tuple[TaskAssignment, WorkerResult]], *, total_tokens: int, elapsed_s: float) -> str | None:
    """四类终止条件：返回触发的原因，None 表示继续。阈值按项目二实测调。"""
    if total_tokens > 60_000 or elapsed_s > 300 or len(history) >= 8:
        return "budget"
    if sum(1 for _, r in history if not r.ok) >= 3:
        return "max_failures"
    if len(history) >= 3:
        recent = {state_fingerprint(history[: i + 1]) for i in range(len(history) - 3, len(history))}
        if len(recent) == 1:  # 连续 3 轮事实集合没变 = 在原地打转
            return "no_progress"
    return None


async def _run_worker(worker: ChatModel, task: TaskAssignment) -> WorkerResult:
    """单个 worker 的最小执行：周三会把它换成 parallel.run_workers 里的并发版本。"""
    payload = json.dumps(task.model_dump(), ensure_ascii=False)
    raw = worker.complete("你是 worker。只输出符合 WorkerResult 的 JSON，约束要原样回传。", payload)
    return WorkerResult.model_validate_json(raw)


async def supervise(objective: str, workers: dict[str, ChatModel], llm: ChatModel) -> dict[str, object]:
    history: list[tuple[TaskAssignment, WorkerResult]] = []
    total_tokens, elapsed_s = 0, 0.0
    while True:
        if (reason := should_stop(history, total_tokens=total_tokens, elapsed_s=elapsed_s)) is not None:
            return {"status": "stopped", "reason": reason, "rounds": len(history), "history": history}
        nxt = decide_next(llm, objective, history)
        if nxt is None:
            return {"status": "done", "rounds": len(history), "history": history}
        worker = workers.get(nxt.assignee)
        if worker is None:  # 分派给不存在的 worker：视为模型输出错误，直接终止而不是重试
            return {"status": "invalid_dispatch", "assignee": nxt.assignee, "history": history}
        result = await _run_worker(worker, nxt)  # 见周三的 parallel.run_workers
        history.append((nxt, result))
```

## 周三 · 并行 worker：并发上限、总超时、失败聚合

**本质**

并行不是一个加速按钮，是把顺序代码里的"错了就停"变成并发代码里的"错了要判定谁错了、要不要等其他、其他要等多久"。这一天的产出物是一段你敢在生产里跑的 fan-out / fan-in 代码。

**Java 视角**

`asyncio.Semaphore` 就是 `ThreadPoolExecutor` 的最大线程数 + 一个 `Guava RateLimiter` 的合体；总超时对应 Feign 里"全局超时"和"单接口超时"必须分别设置，且全局 ≤ 单个 × 并发批次数。失败聚合对应 `CompletableFuture.allOf` 与 `anyOf` 的取舍。

**核心讲解**

- **并发上限必须显式**。不设上限的 fan-out 会一次性打满下游：LLM 供应商的 RPM/TPM 限流、内部 API 的连接池、数据库连接数。经验做法：LLM 类 worker 并发 2–4（不是越快越好，被限流后重试风暴更慢），I/O 类 5–10。
- **两层超时的语义不同**。单任务超时保护"一个 worker 卡死"，总超时保护"整个请求无限期挂着"。只设单任务超时会出事：8 个任务各 40 秒 + 信号量把并发压到 2 → 实际总耗时 160 秒。两个都要设，且要**捕获外层超时后主动取消所有子任务**，否则你的 Agent 在后台继续调工具、继续写数据。
- **结构化并发**。用 `asyncio.TaskGroup`（3.11+）而不是裸 `gather`：任一子任务抛出未捕获异常时，TaskGroup 会取消同组其余任务并等它们退出，避免"主流程已返回、后台还在写库"。若你需要拿到失败清单而不是让它炸出来，就在子任务内部把异常转成结果对象（下面的写法）。
- **失败聚合策略**要按业务选，并在代码里写明是哪一种：`all_required`（任一失败整体失败）、`best_effort`（收多少算多少，但结果必须标注缺失项）、`quorum`（至少 M 个成功）、`fail_fast`（第一个失败立刻取消其余）。项目二默认 `best_effort` + 强制标注，因为分诊场景"少一个服务的结论"仍有价值，但必须显式说明缺了谁。
- **worker 里不许有同步阻塞调用**。一个 `requests.get` 会把整个事件循环冻住，表现是"并发 4 但总耗时等于串行"。诊断：`asyncio.run(debug=True)` 的 slow callback 警告，或在事件循环里挂 `loop.slow_callback_duration = 0.1`。
- **trace 归属**。并发下所有日志混在一起，必须给每个 worker 一个 `worker_run_id`，每条日志带上前缀，否则 W21 接 Langfuse 时你无法把 span 归位。

```python
from __future__ import annotations

import asyncio
import time
import uuid
from enum import Enum
from typing import Awaitable, Callable

from pydantic import BaseModel

from src.agent.supervisor import TaskAssignment, WorkerResult


class AggregateMode(str, Enum):
    ALL_REQUIRED = "all_required"
    BEST_EFFORT = "best_effort"
    QUORUM = "quorum"


class WorkerRun(BaseModel):
    task: TaskAssignment
    result: WorkerResult | None = None
    error: str | None = None
    duration_s: float = 0.0
    run_id: str = ""


Worker = Callable[[TaskAssignment], Awaitable[WorkerResult]]


async def _run_one(worker: Worker, sem: asyncio.Semaphore, task: TaskAssignment, timeout_s: float) -> WorkerRun:
    run = WorkerRun(task=task, run_id=f"{task.assignee}-{uuid.uuid4().hex[:8]}")
    started = time.monotonic()
    async with sem:  # 令牌在这里拿，不在外面：排队时间不计入任务超时
        try:
            async with asyncio.timeout(timeout_s):
                run.result = await worker(task)
        except TimeoutError:
            run.error = f"timeout_after_{timeout_s}s"
        except asyncio.CancelledError:
            raise  # 被总超时取消：立刻交还取消信号，由 run_workers 的收集器补记这次运行
        except Exception as exc:  # noqa: BLE001 —— worker 的异常必须被吃成数据，不能污染兄弟任务
            run.error = f"{type(exc).__name__}: {exc}"[:300]
    run.duration_s = round(time.monotonic() - started, 3)
    return run


async def run_workers(
    workers: dict[str, Worker],
    tasks: list[TaskAssignment],
    *,
    max_concurrency: int = 3,
    per_task_timeout: float = 45.0,
    total_timeout: float = 120.0,
    mode: AggregateMode = AggregateMode.BEST_EFFORT,
    quorum: int = 0,
) -> tuple[list[WorkerRun], str]:
    """fan-out / fan-in：返回 (每次运行的结果, 聚合判定)。判定为 degraded 时上层必须带缺项继续。"""
    sem = asyncio.Semaphore(max_concurrency)
    # 保留 (任务, future) 对：TaskGroup 不会把结果交给你，取消掉的任务也必须能被记账
    futures: list[tuple[TaskAssignment, asyncio.Task[WorkerRun]]] = []
    timed_out = False
    fatal: str | None = None
    try:
        async with asyncio.timeout(total_timeout):
            async with asyncio.TaskGroup() as tg:  # 结构化并发：总超时触发时自动取消并等待全部退出
                for t in tasks:
                    if (worker := workers.get(t.assignee)) is not None:
                        futures.append((t, tg.create_task(_run_one(worker, sem, t, per_task_timeout))))
    except* TimeoutError:
        timed_out = True  # 到这里子任务已被取消，不会再有后台写入
    except* Exception as eg:  # TaskGroup 兜不住的实现级错误：留痕并判失败，不许静默
        fatal = str(eg)[:300]

    runs: list[WorkerRun] = []
    for t, fut in futures:
        if fut.cancelled():  # 被总超时取消的任务：缺谁必须显式可见，否则 supervisor 会以为它成功了
            runs.append(WorkerRun(task=t, error="cancelled_by_total_timeout"))
        elif fut.done() and fut.exception() is not None:
            runs.append(WorkerRun(task=t, error=f"{type(fut.exception()).__name__}: {fut.exception()}"[:300]))
        elif fut.done():
            runs.append(fut.result())
        else:
            runs.append(WorkerRun(task=t, error="not_settled"))

    ok = sum(1 for r in runs if r.result and r.result.ok)
    if fatal is not None or (timed_out and mode is AggregateMode.ALL_REQUIRED) or (ok < len(tasks) and mode is AggregateMode.ALL_REQUIRED):
        return runs, "failed"
    if mode is AggregateMode.QUORUM and ok < quorum:
        return runs, "failed"
    if timed_out or ok < len(tasks):
        return runs, "degraded"  # 禁止把 degraded 当成功返回给 supervisor
    return runs, "ok"


class DummyWorker:
    def __init__(self, delay: float, *, fail: bool = False) -> None:
        self.delay, self.fail = delay, fail

    async def __call__(self, task: TaskAssignment) -> WorkerResult:
        await asyncio.sleep(self.delay)
        if self.fail:
            return WorkerResult(ok=False, facts=[], confidence="low")
        return WorkerResult(ok=True, facts=[f"{task.assignee}:done"], constraints_honored=task.constraints, confidence="high")


if __name__ == "__main__":
    tasks = [
        TaskAssignment(assignee=n, goal=f"分析 {n}", expected_output="WorkerResult", constraints=["只读"])
        for n in ("slow", "fast", "broken")
    ]
    workers = {"slow": DummyWorker(6.0), "fast": DummyWorker(0.2), "broken": DummyWorker(0.2, fail=True)}
    runs, verdict = asyncio.run(run_workers(workers, tasks, per_task_timeout=3.0, total_timeout=20.0))
    print(verdict)  # degraded：broken 失败、slow 超时，fast 仍保留

        print(r.run_id, r.error, r.result.facts if r.result else None)
```

## 周四 · 状态传递：共享 state vs 消息传递

**本质**

两种传递方式各有一种失败：共享 state 的失败是**并发写互相覆盖**，消息传递的失败是**边界处信息丢失**。今天你要亲手制造一次后者，再修掉它。

**Java 视角**

共享可变 state 就是多线程共写一个 `HashMap`——你在 Java 里怎么防，这里就怎么防（不可变消息 + 显式 reducer）。消息传递则是把上下文序列化过网络：跨服务传 DTO 时你会把必填字段做校验，这里同理。

**核心讲解**

**共享 state（LangGraph 里就是那个 `StateGraph` 的 state dict + reducers）**：优点是零序列化成本、worker 能看到彼此成果；风险是两个 worker 同一轮写同一键，后写覆盖先写，而且没有任何报错。规则：每个键必须指定 reducer（`add_messages` 这类"追加"语义，或自定义 merge）；没有 reducer 的键视为只读；写冲突要能检测出来而不是静默 last-write-wins。

**消息传递**：每个 worker 只拿到自己需要的字段，天然并发安全，但每次交接都是一次有损压缩。你项目二的具体失效案例（今天就复现它）：

原始约束是"只允许查询 2026Q2 分区；任何写操作先回主 Agent 确认"。diagnoser worker 的结论被摘要成一句"定位到 order-service 的 12 笔超时"——约束整段消失。supervisor 看到结论后派了下一步"补充查询近 90 天的同类超时"，worker 于是跨分区扫了生产库；因为摘要里也没带"已确认过的写操作范围"，第二个 worker 又重发了一次同样的告警通知。

失效链的三个环节，全部是同一类错误：**约束与权限走自然语言通道，而自然语言通道允许被摘要**。修法不是"提示词里加一句务必保留约束"（它照样会丢），而是：

1. 约束与权限**不进摘要字段**，进 `AgentMessage` 的独立 typed field；组装下一轮上下文时由代码原样拼接，模型无权改写。
2. 在**工具执行之前**加一道确定性校验门：拿 `message.constraints` 里的结构化规则去检查即将执行的工具入参（时间范围、资源前缀、是否写操作），违规直接拒绝并回一条模型可读的错误。这是硬性规则：**边界校验只能在代码里，不能在提示词里**。
3. 交接信息量有下限：`facts` 为空但文本很长的消息直接判为无效。

**代码**

```python
from __future__ import annotations

import re
from datetime import date
from typing import Any, Literal

from pydantic import BaseModel, Field, ValidationInfo, field_validator


class Constraints(BaseModel):
    """约束走结构化通道，永不进入可被摘要的文本。"""

    time_range: tuple[date, date] | None = None
    allowed_source_prefixes: list[str] = Field(default_factory=lambda: ["ticket/"])
    allow_write: bool = False

    @field_validator("time_range")
    @classmethod
    def range_must_be_ordered(cls, v: tuple[date, date] | None) -> tuple[date, date] | None:
        if v and v[0] > v[1]:
            raise ValueError("时间范围倒置")
        return v


class AgentMessage(BaseModel):
    sender: str
    kind: Literal["task", "result", "correction"] = "result"
    facts: list[str] = Field(default_factory=list)
    summary: str = ""  # 只给人读，不参与下一轮决策
    constraints: Constraints
    permission: Literal["read_only", "read_write"] = "read_only"
    confirmed_side_effects: list[str] = Field(default_factory=list)  # 已执行的副作用幂等描述，防重复

    @field_validator("summary")
    @classmethod
    def summary_must_not_carry_numbers(cls, v: str, info: ValidationInfo) -> str:
        # 数字混进摘要 = 下一轮 supervisor 会从散文里二次抽取，迟早漂移。
        # 这是本项目的硬规则：数字只能活在 facts 里。
        facts = info.data.get("facts") or []
        if re.search(r"\d", v) and not facts:
            raise ValueError("摘要含数字但没有 facts：请把数字放进 facts 结构化字段")
        return v


def enforce(msg: AgentMessage, tool: str, tool_args: dict[str, Any]) -> str | None:
    """工具执行前的确定性校验门。返回 None 放行，返回字符串即拒绝（该文本回给模型）。"""
    c = msg.constraints
    if tool.startswith("write_") and not (c.allow_write and msg.permission == "read_write"):
        return f"工具 {tool} 是写操作，本次任务的权限是 {msg.permission}，请回主 Agent 申请确认。"
    if "since" in tool_args and c.time_range is not None:
        since = date.fromisoformat(str(tool_args["since"]))
        if not (c.time_range[0] <= since <= c.time_range[1]):
            return f"入参 since={since} 越界，允许范围 {c.time_range}（该约束不可协商）。"
    if "source" in tool_args:
        src = str(tool_args["source"])
        if not any(src.startswith(p) for p in c.allowed_source_prefixes):
            return f"数据源 {src} 不在白名单 {c.allowed_source_prefixes} 内。"
    return None


def merge_results(existing: list[AgentMessage], new: AgentMessage) -> list[AgentMessage]:
    """reducer：追加而非覆盖，并拒绝'空事实长摘要'的无效交接。"""
    if not new.facts and len(new.summary) > 200:
        return existing  # 记一次 rejected，别让它进入 supervisor 的上下文
    merged = list(existing)
    for m in merged:  # 约束冲突时取更严的一侧，绝不静默放宽
        if m.constraints.time_range is None:
            m.constraints = new.constraints
    merged.append(new)
    return merged
```

## 周五 · handoff 语义

**本质**

handoff（转交）是一次有损的进程交接。它不是"把聊天记录发给下一个 Agent"，而是"把下一个 Agent 完成任务所必须的最小充分集交给它"。交接漏项是排障时最难归因的一类 bug，因为下游看起来一切正常。

**Java 视角**

这跟跨服务传请求上下文是一个问题：你传业务参数，同时必须传 traceId、租户/权限身份、幂等键——最常见的生产事故就是"下游服务丢了租户上下文，用了默认租户"。Agent 的 handoff 丢的是权限上下文，性质完全相同。

**核心讲解**

交接信封必须带四件东西，缺一不可：

1. **目标（goal）**：下游要交付什么、验收标准是什么。写"继续处理这个工单"是无效的，必须写到"给出该工单的根因候选 top3 与证据，不执行任何处置"。
2. **已做事实（established facts）**：已完成且有证据的结论，附引用 ID。注意是"事实"不是"过程"——不要传尝试过但失败的 20 轮，那会诱导下游重复踩。
3. **未决约束与问题（open constraints / open questions）**：还没确认的假设、边界（时间范围、数据源、不得写入）、需要下游回答的问题。这一项最容易被丢，因为它是"没有发生的事"，摘要时最没存在感。
4. **权限上下文（permission context）**：下游能用哪些工具、是否可写、代表哪个用户/角色、已执行过的副作用清单。**硬性规则**：权限上下文由代码从会话状态直接注入，不由模型生成——模型无权扩大权限。

交接的常见失败模式：把全量历史传过去（成本爆炸 + 上游幻觉被下游当成事实接受）；交接即重置（下游完全不知道发生过什么，重复执行副作用——这正是周六要修的）；交接丢失调用者身份（审计断链）。

**代码**

```python
from __future__ import annotations

from typing import Literal

from pydantic import BaseModel, Field, field_validator

from src.agent.state import Constraints


class HandoffEnvelope(BaseModel):
    """交接信封：四件套，任何一项为空都不许发出。"""

    goal: str
    acceptance: str  # 下游怎么判断自己完成了
    established_facts: list[str] = Field(default_factory=list)  # 每条都要带引用
    open_questions: list[str] = Field(default_factory=list)
    constraints: Constraints
    # ↓ 这四组由代码注入，模型不能填（防止交接时扩大权限）
    allowed_tools: list[str] = Field(default_factory=list)
    permission: Literal["read_only", "read_write"] = "read_only"
    acting_as: str = ""
    already_executed_effects: list[str] = Field(default_factory=list)

    @field_validator("goal", "acceptance")
    @classmethod
    def must_be_specific(cls, v: str) -> str:
        if len(v.strip()) < 12:
            raise ValueError("目标/验收标准过于笼统，交接后下游必然自行补全")
        return v

    @field_validator("allowed_tools", "acting_as")
    @classmethod
    def permission_must_not_be_empty(cls, v: object) -> object:
        if not v:
            raise ValueError("缺少权限上下文，拒绝交接：下游会退化成默认权限运行")
        return v


def build_handoff(
    *, goal: str, acceptance: str, facts: list[str], open_q: list[str],
    constraints: Constraints, caller_ctx: dict[str, object],
) -> HandoffEnvelope:
    """caller_ctx 来自会话状态，不是来自模型输出——这是权限注入唯一可信来源。"""
    return HandoffEnvelope(
        goal=goal,
        acceptance=acceptance,
        established_facts=facts,
        open_questions=open_q,
        constraints=constraints,
        allowed_tools=list(caller_ctx["allowed_tools"]),
        permission=caller_ctx["permission"],  # type: ignore[arg-type]
        acting_as=str(caller_ctx["acting_as"]),
        already_executed_effects=list(caller_ctx.get("effects", [])),
    )


def render_for_llm(env: HandoffEnvelope) -> str:
    """给下游的提示词文本；显式声明不可越界的三件事，并要求下游回报时引用同一条 effect。"""
    return (
        f"目标：{env.goal}\n验收：{env.acceptance}\n"
        f"已确认事实：{env.established_facts}\n未决问题：{env.open_questions}\n"
        f"边界：{env.constraints}\n可用工具：{env.allowed_tools}\n"
        f"已执行副作用（不得重复）：{env.already_executed_effects}"
    )
```

**今天的动作**

- [ ] 把 `HandoffEnvelope` 落进 `src/agent/handoff.py`，四个必填校验先跑起来。
- [ ] 故意构造三种残缺交接各一次（无权限上下文 / 无验收标准 / 有副作用清单缺失），确认 pydantic 每次都拒绝。

**会踩的坑**

1. **交接即"把聊天记录贴过去"**。表现：下游成本极高、把上游的错误结论当既定事实继续推。诊断：对比交接文本长度与 `established_facts` 条数。
2. **权限上下文由模型生成**。表现：下游 Agent 报告"我有写权限"，而它本来只有读权限。诊断：检查 `allowed_tools` 是被代码赋值还是从模型输出解析来的。这是安全缺陷，不是 bug。
3. **未决约束丢失**。表现：下游反复做上游已经否决的方案。诊断：把 `open_questions` 打成必填，为空时人工看一轮，通常你会发现它本不该为空。
4. **审计断链**。表现：出了事查不到是谁授权这一步。诊断：`acting_as` 是否为空或写成 "system"。

**自测**

2. 为什么不传完整历史？给出成本与正确性两个理由。

## 本周术语卡

| 术语 | 一句话解释 | 为什么重要 |
|---|---|---|
| orchestrator-worker / supervisor 模式 | 一个不碰业务工具的协调 Agent 负责派活与判定，worker 负责执行 | 你项目二的主结构；supervisor 调工具即结构腐化 |
| hierarchical（层级模式） | supervisor 之上再套 supervisor | 深度每加一层多一次摘要，信息丢失按层数复合，锁两层 |
| context isolation（上下文隔离） | 把高噪声中间过程关进子 Agent，主 Agent 只收结论 | 拆分的三个正当理由之一，其余两个是并行与权限域 |
| permission domain（权限域） | 不同 Agent 挂载不同工具集与读写权限 | 唯一由安全驱动的拆分理由；必须由代码实现，不由提示词实现 |
| fan-out / fan-in | 并发派发多任务再聚合结果 | 并行 worker 的基本形状，聚合策略决定失败怎么算 |
| concurrency limit（并发上限） | `asyncio.Semaphore` 限制同时在跑的任务数 | 不设上限会撞限流；LLM 类经验值 2–4，不是越大越好 |
| total vs per-task timeout | 总超时保护调用方，单任务超时保护卡死者 | 只设单任务超时会出现"12 任务并发 3 = 160 秒"的雪崩 |
| structured concurrency（结构化并发） | `TaskGroup` 在退出时保证子任务全部取消并等待 | 防止接口已返回但后台继续写数据 |
| shared state vs message passing | 共写一份 state，或传不可变消息 | 前者的失败是静默覆盖，后者的失败是边界丢信息 |
| reducer | 指定同一 state 键如何合并（追加/取严/报错） | 没写 reducer 的键应当视为只读 |
| information loss on summarization | 摘要时丢掉约束、置信度与数字 | 本周最难归因的失效链；修法是结构化通道 + 代码校验门 |
| handoff（转交） | 带结构化信封的任务交接 | 交接漏权限上下文 = 下游以默认权限运行，等同跨租户事故 |
