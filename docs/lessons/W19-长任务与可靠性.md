## 周一 · plan-and-execute：把"计划"变成可校验的制品

**本质**：反应式循环（ReAct，W09）每步只决定下一步，"计划"以隐性形式散在上下文里，长任务中会被稀释、被覆盖、被遗忘。plan-and-execute 把计划外化成**结构化制品**：能被程序校验（依赖成环？判据可判定？）、能被修订、能被持久化——"续跑"和"审批"从此才有锚点。

**Java 视角**：等价于把散在 if-else 里的隐式状态改成显式流程定义 + 流程实例。计划就是运行时快照，步骤状态就是节点状态；写过审批流/订单状态机的人这套模型可以直接复用。

**核心讲解**

一份能用的计划有四个字段不可省：**稳定步骤号**（`step_id`，幂等键与续跑定位全靠它，不要用顺序隐式表达）、**意图**、**机械可判定的完成判据**（`done_when`：返回码 / 字段存在 / 阈值比较；写成"确认没问题"等于没写）、**依赖**。步数要封顶（本周用 8）：超了说明某步其实是子任务，该递归而不是把主计划摊长。

修订（replan）的触发条件要写死三条，否则你会走向"从不修订"或"每步重写"两个极端：**① 前置假设被证伪**（判据依赖的事实不成立）；**② 新信息让后续步骤失去意义**；**③ 预算超限**（某步连续撞调用上限）。修订只允许三种动作：追加步骤、把未执行步骤标 `skipped`、改写 `pending` 步骤的判据。**已 `done` 的步骤是不可变事实，永不重写**——这条不是洁癖，它决定你的幂等键能不能算稳。

和反应式的分界线，今天用数据回答而不是感觉：任务 3–5 步内、每步结果决定下一步走向、探索性强 → 反应式更合适（便宜、灵活）。步数到 8–15、有明确终态、要审计和续跑 → 反应式开始出症状：**重复调用同一工具、丢失早期约束（对照 W17 的 `state_fingerprint`）、提前收敛（把中间结果当结论）、上下文里出现自相矛盾的计划**。plan-and-execute 的代价也要记账：多一次规划调用（延迟 + token）、**计划本身会错，而错的计划比没计划更糟**（它给了模型"照着做就对了"的错误安全感）、修订时容易把已完成步骤的事实一起推翻。上下文策略最容易做错的一点：**不要把整份计划每步重放进上下文**——给执行器"计划摘要（目标 + 剩余步骤标题）+ 当前步完整定义 + 上一步产物"，其余靠 `step_id` 去状态里取。

**代码**

```python
"""plan-and-execute 最小骨架：计划是制品，不是提示词装饰。"""
from __future__ import annotations
from typing import Literal
from pydantic import BaseModel, model_validator
class Step(BaseModel):
    id: str                    # 稳定步骤号：幂等键与续跑定位都靠它
    intent: str
    done_when: str             # 可机械判定：返回码/字段存在/阈值，不接受"确认没问题"
    depends_on: list[str] = []
    budget_units: int = 3      # 这步允许几次工具调用；撞顶就失败，别让它无限试
    status: Literal["pending", "running", "done", "failed", "skipped"] = "pending"
class Plan(BaseModel):
    goal: str; steps: list[Step]
    revision: int = 0
    @model_validator(mode="after")
    def valid(self) -> "Plan":
        ids = [s.id for s in self.steps]
        if len(ids) != len(set(ids)) or not 1 <= len(ids) <= 8:
            raise ValueError("步骤 id 要唯一，且主计划 ≤8 步：超了该拆子计划")
        remaining = {s.id: set(s.depends_on) for s in self.steps}
        while remaining:  # 反复剥掉依赖已满足的节点；剥不动就是成环——启动即失败比运行期绕圈好
            ready = {k for k, v in remaining.items() if not v}
            if not ready:
                raise ValueError(f"依赖成环：{sorted(remaining)}")
            remaining = {k: v - ready for k, v in remaining.items() if k not in ready}
        return self
def next_step(plan: Plan) -> Step | None:
    done = {s.id for s in plan.steps if s.status == "done"}  # 依赖满足才放行：续跑从哪儿接着的唯一依据
    return next((s for s in plan.steps if s.status == "pending" and set(s.depends_on) <= done), None)
def revise(plan: Plan, reason: str, additions: list[Step]) -> Plan:
    frozen = {s.id for s in plan.steps if s.status == "done"}  # 已完成步骤不可变：幂等键算稳的前提
    if not reason.strip() or any(a.id in frozen for a in additions):
        raise ValueError("修订必须写理由，且不得重写已完成步骤")
    return plan.model_copy(update={"steps": plan.steps + additions, "revision": plan.revision + 1})
```

## 周二 · 执行隔离：Agent 能跑命令，你就得给它一个牢房

**本质**：只要 Agent 能写代码 / 执行命令，它就是一个**不可信用户**。它执行的每一条命令你都要假设攻击者可控——命令内容可能来自被注入的网页、被污染的工单文本或模型幻觉。隔离不是可选优化，是硬性规则。

**Java 视角**：你从不让业务代码把用户输入拼进 `Runtime.exec()`，也从不让不受信脚本跑在宿主 JVM 里。今天"用户输入"换成了"模型输出"，而模型输出更不可控——它会被上下文里的任何东西说服。

**核心讲解**

隔离层级与各自边界（弱→强）：**进程内 `exec()`**（等于没有隔离，禁止）→ **子进程 + env/路径/超时限制**（挡得住误操作，挡不住蓄意逃逸）→ **容器**（`--network none`、`--read-only`、只 `-v` 白名单目录、`--memory/--cpus/--pids-limit`）→ **gVisor / Firecracker 这类 micro-VM**（真多租户或执行不受信代码时）。选型三问：命令里是否含模型生成的代码？是否有网络出口？一台宿主机跑几个租户？任一条为"是"，子进程方案就不合格。

五条硬性规则：**① 默认拒绝网络**——沙箱一律 `--network none`，需要出口时把域名白名单做在**代理层**，别指望 Agent 自觉（被注入后它会照抄提示里的地址）。**② 路径白名单在最终真实路径上判**——先 `resolve` 再做前缀判断，否则 `../../`、符号链接、绝对路径三种绕法任选一个就出去了；更严的做法是打开时校验（`O_NOFOLLOW`/文件描述符），因为"先校验后打开"存在 TOCTOU（校验完到打开之间目标可被换掉）。**③ 命令用 argv 列表传，永远不用 `shell=True`**——一旦拼 shell 字符串，`;`、`|`、`$()`、反引号就是你的 RCE 入口；参数化 + 命令白名单比"过滤危险字符"可靠一个数量级。**④ 资源上限与硬超时**——CPU/内存/进程数/输出体积都要有顶，超时到点必须**杀整个进程组**（只杀父进程会留下跑飞的孙子进程）。**⑤ 密钥不进沙箱、产物必须小**——不往 env 传凭据（模型可能把它打印出来，日志就留底了），stdout 截断后再进上下文；执行完销毁工作目录，但留一份结构化审计记录（谁、哪个 job、argv、退出码、耗时、产物大小）。

**代码**

```python
"""受限执行：默认拒绝，白名单放行。这是硬性规则，不是建议。"""
from __future__ import annotations
import os, resource, subprocess
from dataclasses import dataclass
from pathlib import Path
@dataclass(frozen=True)
class SandboxPolicy:
    workdir: Path                                 # 唯一可写目录
    allowed_commands: frozenset[str]              # 命令白名单，不是"危险字符黑名单"
    allowed_hosts: frozenset[str] = frozenset()   # 空集 = 断网（默认拒绝）
    timeout_s: float = 25.0
    cpu_s: int = 10
    mem_mb: int = 256
    max_output_bytes: int = 200_000
def _resolve_within(root: Path, candidate: str) -> Path:
    real_root, p = root.resolve(), (root / candidate).resolve()
    if p != real_root and real_root not in p.parents:  # 先 resolve 再判：挡 .. 与符号链接
        raise PermissionError(f"路径越界，拒绝：{candidate}")
    return p
def run_in_sandbox(policy: SandboxPolicy, argv: list[str], *, cwd: str = ".") -> str:
    if argv[0] not in policy.allowed_commands:
        raise PermissionError(f"命令不在白名单：{argv[0]}")
    workdir = _resolve_within(policy.workdir, cwd)
    env = {k: os.environ[k] for k in ("PATH", "HOME") if k in os.environ}  # env 白名单：凭据进不去
    def _limits() -> None:  # POSIX 下 fork 后生效；容器里等价限制写在 run 参数上
        resource.setrlimit(resource.RLIMIT_CPU, (policy.cpu_s, policy.cpu_s))
        resource.setrlimit(resource.RLIMIT_AS, (policy.mem_mb << 20, policy.mem_mb << 20))
        resource.setrlimit(resource.RLIMIT_NPROC, (64, 64))
        os.setsid()                     # 新进程组：超时要能连孙子一起杀
    try:
        r = subprocess.run(argv, cwd=workdir, env=env, shell=False,  # 硬规则：绝不 shell=True
                           capture_output=True, text=True, timeout=policy.timeout_s, preexec_fn=_limits)
    except subprocess.TimeoutExpired:
        raise RuntimeError(f"超过 {policy.timeout_s}s，已终止整个进程组") from None
    if r.returncode != 0:               # stderr 截断后交回模型：它需要知道为什么失败
        raise RuntimeError(f"退出码 {r.returncode}\n{r.stderr[:500]}")
    return r.stdout[: policy.max_output_bytes]
# 下一层真隔离（跑模型生成的代码或多租户必须上）：
# docker run --rm --network none --read-only --memory 256m --cpus 1 --pids-limit 64 --user 65534
#   -v "$WORK:/work:rw" -v "$REPO:/repo:ro" …
```

## 周三 · 重试、幂等、断点续跑：Java 三板斧的直接迁移

**本质**：本周核心。对应关系很直接：**事务边界 = 副作用提交点**、**幂等键 = 去重表**、**补偿 = Saga**、**先写意图再执行 = outbox**。Agent 新增的变量只有两个：步骤序列不确定（模型决定）、崩溃点任意（可能在第 3 步和第 4 步之间被 kill）。结论：状态必须**外置**，副作用必须**先记账再做**。

**Java 视角**：你处理过 MQ 的 at-least-once 重复投递，也写过消费端去重表。今天把"消费者"换成"可能被重启的执行器"，问题结构完全一样：重复投递 + 无事务边界的副作用 = 必须靠幂等键解决，而键必须能从输入**推导**出来，不能是随机数。

**核心讲解**

先给每个有副作用的工具定级（今天的主产出物）：

| 级别 | 例子 | 重试策略 | 键与存储 |
|---|---|---|---|
| `read` 纯读 | 查错误率、读文档 | 随便重试 | 不需要键 |
| `idem` 幂等写 | 按 ID 覆盖写、带唯一约束的创建 | 重试安全 | 键 + UNIQUE |
| `mutate` 非幂等写 | 改状态、追加行、内部群通知 | 键 + 前置状态检查 + 补偿计划 | 键 + intent/done 两态账本 |
| `irreversible` 不可逆 | 对外通知、转账、删生产数据 | **永不自动重试**；命中未完成记录就停下交人工 | 键 + 审批记录（周五） |

幂等键组成 = **业务身份 + 步骤身份 + 工具名 + 规范化参数摘要**，写成 `thread_id : step_id : tool : sha256(canonical_json(args))`。三条规则是关键：**① 用计划步骤号，不要 `uuid4()`**——随机键重启后就变了，等于没有键；**② 不要把 LLM 生成的自由文本放进摘要**（同一步重跑措辞会变，键就漂了），只放 ID、枚举、数值；**③ 摘要用 `sort_keys=True` 的规范化 JSON**，否则 `{"a":1,"b":2}` 与 `{"b":2,"a":1}` 会被算成两次操作。存储：有 **UNIQUE 约束**的表或 `SET key NX EX ttl`；"先 SELECT 再 INSERT"不加约束必有竞态（两个 worker 同时读到"没做过"）。

执行顺序不能反：**begin(intent) → 真执行 → complete(result)**。重启后见到 `intent` 却无 `done`，说明"做过一半"——幂等动作可重做，`mutate` 按补偿计划处理，`irreversible` 必须停。这就是 outbox/意图日志的全部价值：把"我不知道有没有成功"变成"我有明确分支"。重试规则照抄你熟悉的：只对可重试错误（超时、连接失败、429/5xx）重试，指数退避 + jitter + 次数上限 + 总预算；**绝不重试**两类——模型语义错误（重试十次也一样错，该改的是 W18 的 schema 约束与描述）和无键的非幂等写（重试 = 重复副作用）。

断点续跑：图状态用 checkpointer 持久化、恢复靠同一 `thread_id`、`get_state(cfg).next` 指出挂在哪个节点。**但 checkpoint 存的是图状态，不是外部世界**：checkpoint 说"这步没做"，而通知可能已经发出去了。所以续跑一定重放那一步的工具调用，安不安全全看今天的账本——这就是周六实验的假设，也是本周验收项的内核。

**代码**

```python
"""副作用账本 + 幂等键：崩溃在任意一步都不该重复发通知/写数据。"""
from __future__ import annotations
import asyncio, hashlib, json, random, sqlite3, time
from dataclasses import dataclass
from enum import Enum
from typing import Any
RETRYABLE = (TimeoutError, ConnectionError, OSError)  # 按真实上游补：429/5xx 归一成这几类再进来
class Effect(str, Enum):
    READ = "read"                  # 随便重试
    IDEMPOTENT = "idem"            # 同键重放 = no-op
    MUTATING = "mutate"            # 键 + 前置检查 + 补偿
    IRREVERSIBLE = "irreversible"  # 永不自动重试；未完成就停下交人工
@dataclass(frozen=True)
class Call:
    thread_id: str
    step_id: str                    # 来自计划步骤号；用 uuid4 等于放弃幂等
    tool: str
    args: dict[str, Any]
    def key(self) -> str:  # 规范化 JSON 再摘要：键顺序与 LLM 自由文本都不能进摘要
        blob = json.dumps(self.args, sort_keys=True, ensure_ascii=False, default=str)
        return f"{self.thread_id}:{self.step_id}:{self.tool}:{hashlib.sha256(blob.encode()).hexdigest()[:16]}"
class Ledger:
    """一张表 = Java 的去重表 + outbox；PRIMARY KEY 是竞态的最后兜底。"""
    def __init__(self, path: str) -> None:
        self.db = sqlite3.connect(path, check_same_thread=False)  # 访问统一走 to_thread
        self.db.execute("PRAGMA journal_mode=WAL")
        self.db.execute("CREATE TABLE IF NOT EXISTS effects("
                        "key TEXT PRIMARY KEY, tool TEXT, state TEXT, result TEXT, ts REAL)")
    def begin(self, key: str, tool: str) -> tuple[bool, str | None]:
        try:  # 先写意图再执行：崩溃后能看到"打算做但没记完"
            self.db.execute("INSERT INTO effects VALUES(?,?,?,NULL,?)", (key, tool, "intent", time.time()))
            self.db.commit()
            return True, None
        except sqlite3.IntegrityError:  # 已存在：把上次结果原样还回去，副作用不重放
            state, result = self.db.execute("SELECT state, result FROM effects WHERE key=?", (key,)).fetchone()
            return False, result if state == "done" else f"INCOMPLETE:{state}"
    def complete(self, key: str, result: str) -> None:
        self.db.execute("UPDATE effects SET state='done', result=? WHERE key=?", (result, key))
        self.db.commit()
async def call_idempotent(ledger: Ledger, call: Call, effect: Effect, fn, *, retries: int = 3) -> Any:
    fresh, cached = await asyncio.to_thread(ledger.begin, call.key(), call.tool)
    if not fresh:
        if cached and not str(cached).startswith("INCOMPLETE"):
            return json.loads(cached)  # 幂等命中：这条日志就是"不重复副作用"的证据
        if effect in (Effect.MUTATING, Effect.IRREVERSIBLE):
            raise RuntimeError(f"{call.key()} 上次未完成且属 {effect.value}：走补偿或人工，不自动重放")
    for attempt in range(retries):
        try:
            out = await fn(**call.args)
        except RETRYABLE:              # 只重试这类；语义错误重试无用
            await asyncio.sleep(min(2 ** attempt + random.random(), 15))  # jitter：别同批任务同刻重试
            continue
        await asyncio.to_thread(ledger.complete, call.key(), json.dumps(out, ensure_ascii=False, default=str))
        return out
    raise RuntimeError(f"{call.tool} 连续 {retries} 次可重试失败：停下，别让循环烧预算")
```

## 周四 · 异步与队列：长任务不该占着请求线程

**本质**：20 分钟的任务不该让调用方等 20 分钟。模式你很熟：**提交 → 后台执行 → 轮询或订阅 → 取结果**。新增的只有一件事：job 内部不确定（会中断、会等审批、会失败），所以**状态机必须显式**——可查询、可取消、可恢复。

**Java 视角**：MQ + 消费者 + 任务表。差别是这里"消费者"是有状态的图执行器：worker 崩溃不等于任务失败，它该被另一个 worker 从 checkpoint 接着跑——靠的正是周三的账本 + `thread_id`。

**核心讲解**

状态机至少七个态：`PENDING / RUNNING / WAITING_APPROVAL / NEEDS_INPUT / SUCCEEDED / FAILED / CANCELLED / TIMED_OUT`。两个"等人"的中间态不是装饰：轮询端必须能区分"还在跑"和"在等人"，否则用户体验就叫"卡住了"。`job_id` 与 `thread_id` 一一对应，这是恢复语义的锚。

两个不同的闹钟（最常漏的一条）：**排队超时**（排不到 worker 就明确拒绝、返回 429，别在内存里堆着假装在跑）与**执行超时**（跑起来了但太久，`asyncio.timeout` 杀掉并标 `TIMED_OUT`）。并发分三层：worker 数（进程内并发）、每租户并发、每模型 RPM/TPM 令牌桶——LLM 限流按**分钟**计，你的重试与批量并行特别容易撞它（W06 的退避在这里再用一次）。取消要小心：`task.cancel()` 在 await 点抛 `CancelledError`，它**不是 `Exception` 子类**，`except Exception` 接不住；而且取消路径要**先记账再退出**，否则续跑会重放已执行步骤。订阅 vs 轮询：轮询简单、能穿代理和网关；订阅（SSE/WebSocket/回调）省往返但断线后要能补状态——所以订阅通道只传"状态变了，来拉一次"，别当可靠传输用。

选型诚实说：今天这个进程内 `asyncio.Queue` **重启即丢**，只适合单机演示与学习。生产排序（知道定位即可，别现在全上）：Redis Streams / RabbitMQ（任务分发 + 持久）→ Celery / Dramatiq（成熟 worker 生态，但把 LLM 循环塞进一个 task 会让重试语义很难看）→ Temporal 这类持久工作流引擎（把"崩溃后从哪儿继续"交给引擎，代价是部署与心智负担）。关键区分：**LangGraph 的 checkpointer 解决"图状态续跑"，broker 解决"任务不丢"，两者不能互相替代**。`# 2026 年各框架的 Agent 支持面请核对官方文档，本周只做定位判断`。

```python
"""后台 job + 轮询/订阅：进程内实现，明确它的重启语义（重启即丢，别当生产方案）。"""
from __future__ import annotations
import asyncio, uuid
from dataclasses import dataclass, field
from enum import Enum
class JobState(str, Enum):
    PENDING = "pending"; RUNNING = "running"; WAITING = "waiting_human"  # 等人 ≠ 还在跑：轮询端必须分得开
    SUCCEEDED = "succeeded"; FAILED = "failed"; CANCELLED = "cancelled"; TIMED_OUT = "timed_out"
@dataclass
class Job:
    id: str; thread_id: str; payload: dict    # 一个 job 绑一个 thread_id：恢复锚就在这，对外句柄即 jid
    state: JobState = JobState.PENDING
    watchers: list["asyncio.Queue[JobState]"] = field(default_factory=list)
class JobRunner:
    def __init__(self, workers: int = 3, *, queue_wait_s: float = 60.0, job_timeout_s: float = 300.0) -> None:
        self.q: asyncio.Queue[Job] = asyncio.Queue(maxsize=workers * 4)  # 有界队列 = 背压
        self.jobs: dict[str, Job] = {}
        self.n, self.wait_s, self.job_s = workers, queue_wait_s, job_timeout_s
        self._tasks: list[asyncio.Task] = []   # 必须持引用：裸 create_task 会被 GC，任务凭空消失
    def start(self) -> None:
        self._tasks = [asyncio.create_task(self._worker()) for _ in range(self.n)]
    async def submit(self, payload: dict) -> str:
        job = Job(id=(jid := uuid.uuid4().hex), thread_id=jid, payload=payload)  # 成对生成，别分两次算
        self.jobs[jid] = job
        try:
            await asyncio.wait_for(self.q.put(job), self.wait_s)  # 闹钟一：排队超时 ≠ 执行超时
        except TimeoutError:
            job.state = JobState.FAILED
            raise RuntimeError("队列已满：明确拒绝（宁可 429，别在内存里堆着假装在跑）") from None
        return jid
    async def _run(self, job: Job) -> object: ...   # 你的图 invoke：崩溃后靠 checkpoint + 账本接着跑
    async def _worker(self) -> None:
        while True:
            job = await self.q.get()
            try:
                async with asyncio.timeout(self.job_s):          # 闹钟二：执行超时
                    job.state = JobState.RUNNING
                    await self._run(job)
                    job.state = JobState.SUCCEEDED
            except TimeoutError:
                job.state = JobState.TIMED_OUT                    # 超时也要落状态，轮询端才分得清
            except asyncio.CancelledError:                        # 它不是 Exception 子类，必须单独接
                job.state = JobState.CANCELLED                    # 先记账再退出，否则续跑重放副作用
                raise
            except Exception:                                     # noqa: BLE001  任务级兜底
                job.state = JobState.FAILED
            finally:
                for q in job.watchers:
                    q.put_nowait(job.state)     # 订阅只传"变了"；断线后回来看表，轮询才是底
                self.q.task_done()
    def poll(self, jid: str) -> JobState:
        return self.jobs[jid].state                # 轮询端就这一行：简单、能穿代理与网关
    def watch(self, jid: str) -> asyncio.Queue:
        q: asyncio.Queue = asyncio.Queue(); self.jobs[jid].watchers.append(q); return q
```

## 周五 · 人机协同：审批门、部分执行、回滚

**本质**：高风险动作要停下来等人点头。设计要点不是"弹窗"，而是**等待可持久**（进程可退出、换机器也能回来继续）、**信息足够做决定**、**超时默认拒绝**。

**Java 视角**：审批流的用户任务（User Task）+ 超时升级 + 双人复核，规则全适用；唯一变化是"表单内容"由 Agent 生成，所以它必须被校验——不能模型写什么审批人就信什么。

**核心讲解**

三条硬性规则：**① 高风险动作必须有审批门，判据写在配置里而不是提示词里**——阈值来源是结构化事实：影响行数、是否生产、金额、是否对外可见、能否补偿；写进 prompt 的"请谨慎操作"没有约束力，模型会说服自己。**② 等待必须是可持久状态**——用 W10 的 `interrupt(payload)` + checkpointer：抛中断 → 图停住、快照落盘 → 进程可以退出 → 任何时刻带 `Command(resume=...)` 回来；等待三小时与三秒钟机制相同。**③ fail-closed**——无人应答 / 超时 / 审批人身份不明一律拒绝，默认放行等于没有门；审批记录（谁、何时、对哪个 `payload_sha` 说了 yes）是要落盘的审计制品。

一条合格待办的四要素：**将要发生什么**（动作 + 目标资源，用 ID 不用模型转述）、**影响面**（多少行、多少服务、是否对外可见）、**证据**（触发它的告警/查询结果摘要 + 数据来源）、**补偿路径**（可补偿就写怎么补，不可补偿就明写"不可逆，需二次确认"）。再加 `payload_sha`：批准后实际执行的参数必须与审批时看到的一致，否则中途被改你看不出来（审批版的 TOCTOU）。机制上别忘了 **resume 会重跑整个节点**，所以 `interrupt()` 之前只允许纯读；审批通过后执行的那一步仍要走周三的幂等账本——**"批准"和"执行"之间也可能崩**。

部分执行：批量动作不要一次全放，按 **dry-run → 首批小范围（1 个对象）→ 观察 → 全量**推进，每批之间留可中断点。回滚分两类：可补偿（留反向操作记录或版本化覆盖）与不可补偿（对外通知、已发消息）——后者在计划阶段就标 `IRREVERSIBLE` 并要**二次确认**（第一次问"要不要做"，第二次问"确认这不可逆"）。分层选择：W18 的 elicitation（MCP 层）适合工具执行**中途**的小确认（往返短、贴宿主 UI）；LangGraph 的 `interrupt` 适合跨小时/跨天的审批（状态可查、可换人审）。两者不冲突，也别用一个硬套另一个的场景。

from __future__ import annotations
import hashlib, json
from typing import TypedDict
from langgraph.checkpoint.sqlite import SqliteSaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt
# 硬规则：哪些动作必须审批，来自配置与结构化事实，不来自提示词
NEED_APPROVAL = {"close_ticket", "notify_oncall", "rollback_deploy"}
COMPENSATION = {"close_ticket": "reopen_ticket(id)",
                "rollback_deploy": "不可逆：外部部署系统无回滚 API"}
class GraphState(TypedDict):
    plan_digest: str
    pending_action: dict      # {"tool":…, "args":…, "rows":…, "prod":True}
    approved: bool
def gate(state: GraphState) -> dict:
    a = state["pending_action"]
    if a["tool"] not in NEED_APPROVAL and not a.get("prod"):
        return {"approved": True}                    # 低风险直接放行，别把人淹成橡皮图章
    sha = hashlib.sha256(json.dumps(a, sort_keys=True, default=str).encode()).hexdigest()[:12]
    decision = interrupt({          # 之前不得有任何写：resume 时本节点从头再跑（W10 铁律）
        "question": f"是否对 {a['args'].get('service')} 执行 {a['tool']}？",
        "facts": {"影响行数": a["rows"], "环境": "生产" if a.get("prod") else "预发",
                  "计划": state["plan_digest"], "补偿": COMPENSATION.get(a["tool"], "未定义→视为不可逆"),
                  "payload_sha": sha},
        "options": ["approve", "reject", "modify"],
        "default": "reject",        # fail-closed：超时/无人应答 = 拒绝
    })
    return {"approved": decision == "approve", "pending_action": {**a, "sha": sha}}
def apply_action(state: GraphState) -> dict:  # 审批通过后仍走周三账本：批准与执行之间也可能崩
    return {"approved": False}
b = StateGraph(GraphState)
b.add_node("gate", gate)
b.add_node("apply", apply_action)
b.add_edge(START, "gate")
b.add_conditional_edges("gate", lambda s: "apply" if s["approved"] else END, {"apply": "apply", END: END})
b.add_edge("apply", END)
cfg = {"configurable": {"thread_id": "p2-incident-42"}}   # 有 checkpointer 必须给 thread_id（W10）
with SqliteSaver.from_conn_string("checkpoints.sqlite") as saver:
    app = b.compile(checkpointer=saver)
    app.invoke({"plan_digest": "W19 计划 v3", "pending_action":
                {"tool": "notify_oncall", "args": {"service": "order-service"}, "rows": 1, "prod": True}}, cfg)
    snap = app.get_state(cfg)
    print(snap.next, snap.tasks[0].interrupts[0].payload["facts"])  # 挂在哪、待办内容是什么
    app.invoke(Command(resume="approve"), cfg)                       # 换进程、换天回来也一样

## 本周术语卡

| 术语 | 一句话解释 | 为什么重要 |
|---|---|---|
| plan-and-execute | 先产出结构化计划再按步执行、支持修订 | 计划可校验、可续跑、可审批 |
| 计划修订 / replan | 按固定触发条件追加或改写未完成步骤 | 已完成步骤不可变，否则幂等键算不稳 |
| 完成判据 / done_when | 每步机械可判定的成功条件 | 不可判定的判据让"完成"变成自我宣布 |
| 执行隔离 / sandboxing | 受限环境 + 资源上限 + 网络与路径白名单 | 模型输出比用户输入更不可信；硬性规则 |
| TOCTOU | 校验与使用之间的竞态（路径、审批 payload） | 校验要在最终真实路径上、执行前重算 |
| 幂等键 / idempotency key | 业务身份 + 步骤 + 工具 + 规范化参数摘要 | 随机 UUID 在重启后失效 |
| 意图日志 / outbox | 先记 intent，执行后标 done | 把"不知道有没有成功"变成明确分支 |
| 补偿 / compensation | 非幂等写的反向操作或人工兜底 | 不可逆动作永不自动重试 |
| 副作用分级 | read / idempotent / mutating / irreversible | 决定重试与审批策略 |
| at-least-once | 至少投递一次，因此消费端必须去重 | 你的老问题，今天的同一结构 |
| 背压 / bounded queue | 有界队列 + 排队超时拒绝 | 队列满时明确失败比堆着强 |
| 审批门 / human-in-the-loop | 高风险动作停在可持久状态等人 | fail-closed：无响应即拒绝 |
| checkpoint 续跑 | 用 `thread_id` 从持久化图状态恢复 | 图状态一致 ≠ 外部世界没重复副作用 |
