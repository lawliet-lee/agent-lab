## 周一 · 一页 PRD：把"排障助手"变成可验收的东西

**本质**：PRD 在本项目的职能不是文档礼仪，是**把模糊愿望压成可判定的通过标准**。其中最值钱的是那 3 个真实样例：它们今天界定范围，周五当验收脚本，W21 直接长成评测集种子（30 条里的头 3 条）。写不出样例=需求还没想清，这个信号同样值钱。

**Java 视角**：等价于接口文档 + 验收测试用例前置（TDD 的 AT 层）。你做微服务时"先定契约再开发"的习惯原样适用，只是契约另一方是个概率模型——所以失败语义（第 3 节）比正常路径更值得写。

**核心讲解**：一页纸，六节，每节都有"不写会怎样"：

1. **目标用户与触发场景**（2 行）：谁、在什么时刻打开它。反例"帮助研发排障"太宽；正例"值班同学在收到告警、拿到异常堆栈后 3 分钟内要一个可行动的初步结论"。场景越具体，工具集越收敛。
2. **输入 / 输出契约**（各 3-5 行，写成字段）：输入=异常堆栈或错误码+服务名+时间范围；输出=结构化 JSON（根因假设、证据行引用、建议动作、置信度）。这一节直接决定 W09 周四的 validator schema，别空对空。
3. **明确不做什么**（≥3 条）：不执行任何变更命令、不连生产库、不给未经来源支持的结论。"不做"清单是范围保护——第 5 周它还保护你不把自己淹死。
4. **3 个真实样例**（本节核心）：从你最近值班记录里挖真实 case，别编。每条含：输入原文、期望输出要点、**机器可判的通过标准**（"输出的 root_cause 包含关键实体 X 且引用的证据行全部真实存在于样本日志中"——能用 `validate_final` 那种程序判定最好，语义判定写清楚标准即可）。
5. **成功度量**（1-2 行）：v1 阶段就是"3 条样例 ≥1 条全链路跑通且输出可人工判对"。
6. **运行形态**：CLI 优先（铁律：不碰前端，计划里写明的非目标）。

样例的配比有讲究：**2 条单跳**（一次检索可答）**+1 条多跳**（必须两次以上工具调用）——多跳那条就是给 agent 循环本身做验收，纯单跳的样例组 workflow 也能过，证明不了你的循环work。

**参照骨架**（日志排障助手，节选）：

```markdown

S1（单跳）输入：java.lang.OutOfMemoryError: Java heap space, 服务 order-svc, 02:15
期望输出要点：指出 heap OOM；引用样本日志中 -Xmx 配置行与 GC 日志行；建议 dump+检查大集合。

期望：连接池耗尽；引用池配置行+等待超时行；建议查泄漏连接而非调大池（置信 medium）。
S3（多跳）输入：checkout-svc 间歇 504，无明确异常栈

## 4. 不做什么
不做：自动重启/改配置/执行 SQL/解释与代码无关的网络问题（直接说超范围并给转交对象）。
```

## 周二 · 工具集设计：入参、返回、失败语义

**本质**：工具是 agent 的手。模型可以平庸，手必须清晰——工具契约的质量直接决定循环的步数和错误率。每个工具回答三个问题：怎么调（入参 schema）、返回什么（结构，不是字符串海）、**怎么失败**（错误码+语义，这条最常被跳过）。

**Java 视角**：就是给外部（模型）暴露的 API 设计评审。你不会让 REST 接口返回裸 String 或把所有异常吞成 500；这里同理，模型读不懂含糊的失败，就会瞎猜下一步。**你和纯算法背景同事的差距从今天开始体现。**

**核心讲解**：

工具数量 3-5 个，宁少勿多——每多一个，模型的选择题就难一分（工具误选率随数量上升，schema 也每个都吃 input token）。日志排障助手的参照集：

1. `search_logs`：按 关键词/错误码 + 服务 + 时间窗 检索日志，返回命中行（截断+行号）。
2. `read_log_context`：给 `file` + `line` + `window`，返回该行前后上下文。用于"搜到后再细看"，把大文件切小块进上下文——W07 截断策略的工具化。
3. `get_service_meta`：服务名 → 部署信息/依赖/负责人。为多跳样例（级联故障）提供下游线索。
4. （可选）`grep_exception_pattern`：按异常类名聚合出现次数/时间分布。

**返回结构铁律**——统一信封：

```json
{"ok": true,  "data": {"hits": [{"file": "order.log", "line": 4512, "ts": "...", "text": "..."}], "total": 37, "truncated": true}, "error": null}
{"ok": false, "data": null, "error": {"code": "NO_MATCH", "message": "时间窗内无命中", "hint": "扩大时间窗或换关键词"}}
```

失败语义要区分**有信息量的失败**和**故障**，模型对前者的反应是改策略、对后者只能放弃：

| code | 语义 | 期望的模型行为 |
|---|---|---|
| `NO_MATCH` | 查询合法但没结果 | 换关键词/扩时间窗重试（这是有用信号！） |
| `BAD_PARAM` | 入参不合 schema | 按 message 修正重试一次 |
| `TIMEOUT`/`IO_ERROR` | 基础设施故障 | 重试≤1 次，仍败则降级答复 |
| `OUT_OF_SCOPE` | 超出数据边界 | 停止并说明超范围 |

`hint` 字段是被低估的设计：错误信息里带"下一步建议"，模型的修复成功率肉眼可见地上升——本质是把你的领域知识写进失败路径。**危险操作确认（本周参照集里没有写操作；若你选题含 UPDATE 类，必须 requires_confirmation 并接 W10 周四的 confirm 节点）**。**密钥与环境：数据准备时生产日志一律脱敏后入样本（客户身份、token、内网 IP），`.env` 管 API key，样本数据目录进 `.gitignore`，仓库只放合成/脱敏样例——"密钥与业务敏感数据不入仓库"从项目一第一天就是硬习惯，不是 W22 才学。**

数据准备（今天后半 30'）：真实日志脱敏后截 2-5 个典型故障场景各一个窗口段，放 `projects/p1/data/`，**每条 PRD 样例的期望证据行号在这批样本里真实存在**（拿 `grep -n` 验证）——样例和数据的对应关系要像外键一样对上，对不上周五必翻车。

## 周三 · Agent 骨架：空工具也要跑通全链路

**本质**：今天的成功标准只有一个——**用返回假数据的 stub 工具，让"问进答出"的完整链路在图上跑通**：图执行、消息流转、校验、trace 全环节就位。这是"先跑通再跑好"的具体操作化：周四之后你接真实工具时，任何 bug 都能立刻归因到"是这个工具的问题"，因为链路其他部分已被证明是通的。集成测试里先桩后真的道理你懂，这里是先桩后开发。

**Java 视角**：完全等价于 Spring 集成测试里 `@MockBean` 打底：先把 wiring（装配）验对，再逐个换真实现。反模式也同款：一边写业务一边调框架，报错时不知道怪谁。

**核心讲解**：

节点划分直接用 W10 周六迁移成果，加一个入口出口约定：

```
START → agent_turn（模型带 tools） → route ─┬→ tools（执行工具回填）→ agent_turn
                                            ├→ validate（契约校验）─┬→ agent_turn（回喂错误，≤2轮）
                                            │                        └→ END
                                            └→ END（熔断：步数/预算/超限降级）
```

日志排障助手的状态定义：`question`、`messages`（reducer add）、`observations`（工具返回累积，供 validate 核对引用真实性）、`attempts/repairs`、`trace_ok`。trace 节点沿用 W09 Tracer，session 目录换成 `projects/p1/runs/`。

**stub 怎么写才算合格**：不是返回 `{}`，而是**返回符合周二 `ToolResult` schema 的固定假数据**。两个理由：(1) 信封结构错了当场被 pydantic 拦，模型不会被野格式带偏；(2) 周四换真实实现时，接口签名/返回类型不变，图不用改一行——这叫把变更面钉死在单点。stub 数据从你的样本日志里剪两段真的塞进去，让"假数据"至少在格式和内容上都逼真。

今天还有一个容易被跳过的决策：**图入口的调用形态**定下来——`answer(question: str, session_id: str) -> FinalReport`，内部组装 config（thread_id + recursion_limit）。周四的单元测试、周五的样例验收、W12 的持久化全部挂在这个签名上，改它的成本越晚越高。

**代码**：`projects/p1/graph.py` 关键骨架（组装部分你按 W10 熟练度自己补，今天是体力活不是新知识）：

## 周四 · 真实化前 2 个核心工具 + 单元测试

**本质**：把 `search_logs` 和 `read_log_context` 从 stub 换成真实现（读本地样本），并给它们写单元测试。选工具的优先级只有一个判据：**PRD 样例离不开谁先做谁**——看你的 eval_seed，每条样例的证据行主要出自哪两个工具。剩下工具保持 stub 到下周，链路不断。

**Java 视角**：今天就是普通的"实现 + JUnit"日。新鲜处只有两点：(1) 被测函数吃的是 JSON Schema 约束的入参，测试用例里要包含**畸形入参**（模型给的机会比同事多得多）；(2) 你的断言对象是返回信封——`ok/error.code/data 字段形状`，不是某个内部变量。

**核心讲解**：

`search_logs` 真实现 v1 不要上搜索引擎：**`pathlib.rglob` + 逐行正则扫文本文件**足够，样本几百 MB 也能秒级完成（先 `grep` 风格预筛时间窗再精扫）。先跑通再跑好——BM25/向量检索是 W13 的课，今天做了就是本周的失控点，记进 backlog。

失败语义在实现里的映射要当场对：文件不存在→`IO_ERROR`；时间窗格式非法→`BAD_PARAM`（message 里带期望格式示例）；扫描无命中→`NO_MATCH`+hint（建议扩窗）。**命中行截断**：单条命中 `text` 截 300 字并加 `truncated: true`（W07 预算，工具侧做，别指望模型自己节制）。

测试的三个层次（pytest）：

```python
import pytest
from projects.p1.tools.search import search_logs
from projects.p1.tools.result import ToolResult   # pydantic 信封

def test_hit_with_line_numbers(sample_dir):
    r = ToolResult.model_validate(search_logs({"query": "OutOfMemoryError",
                                               "service": "order-svc",
                                               "time_from": "02:00", "time_to": "02:30"}))
    assert r.ok and r.data["hits"][0]["line"] > 0
    assert all(len(h["text"]) <= 300 for h in r.data["hits"])

def test_no_match_carries_hint(sample_dir):
    r = ToolResult.model_validate(search_logs({"query": "NPE_IN_A_VACUUM",
                                               "service": "order-svc",
                                               "time_from": "00:00", "time_to": "00:10"}))
    assert not r.ok and r.error["code"] == "NO_MATCH" and "hint" in r.error

@pytest.mark.parametrize("bad", [{"service": ""}, {"time_from": "昨天"}, {}])
def test_bad_param(sample_dir, bad):        # 模型发的畸形入参：返回 BAD_PARAM，不许抛 Python 异常出界
    r = ToolResult.model_validate(search_logs(bad))
    assert not r.ok and r.error["code"] == "BAD_PARAM"
```

## 周五 · 端到端打通：让第一条真实样例过关

**本质**：把 `get_service_meta`（stub 或真实）留到下周，今天所有注意力放在**PRD 的 S1 样例端到端真实通过**——真实工具、真实 trace、校验器放行、输出可人工判对。"通过"由机器判定（eval_seed 里的 standard），不是你觉得差不多。今天的通过率预期本来就该低于 100%，失败不是倒退，是 W12 的输入。

**Java 视角**：联调日。你只需要克制住联调时最容易犯的错：改了 prompt 感觉"顺眼"就当修复。这里一律以样例复跑结果为准——W05 的 A/B 习惯今天开始吃它自己的狗粮。

**核心讲解**：

打通的迭代节奏固定成四步循环（今天大概跑 3-5 轮）：

1. `python -m projects.p1.run_eval --id S1`：输出 `PASS/FAIL + 失败字段明细 + trace 路径`。
2. FAIL 时**先分类再动手**：协议错（模型输出不合 schema）→ 改 prompt 契约示例；检索错（工具没找对）→ 改工具或 hint；推理错（输入都对但结论歪）→ 记 backlog，v1 不修（别 today 改 system prompt 玄学）。
3. 每次只改一处，复跑，记录本轮改动与结果——这份记录就是 PR commit message 和 W12 code review 的原料。
4. 修 S1 成功后，**至少再看一眼 S2**：确认不是过拟合单条样例（改了个只对 S1 起作用的硬编码 hint 就是过拟合的味道）。

顺带把成本仪表装好（10 分钟的事，W22 的地基）：eval 脚本末尾打印本次运行的 trace 汇总——总步数、总 token、估算成本。死循环烧钱的事在 W06 周四领教过，现在它是你的生产风险：**每个可复跑入口都要带成本读数**。
